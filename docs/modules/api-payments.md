# api-payments Module

> **Living document.** Read this before modifying the module. Update it in the same change whenever the module's behavior, endpoints, files, or dependencies change.

**Source:** `api/src/modules/payments/` (+ `packages/shared/src/api.ts`'s `PaymentRequestSchema`/`PaymentResponseSchema`) · **Last verified:** 2026-07-23 (fix wave: `destination` now checksum-validated via `StrKey` in `service.ts`, `PaymentRequestSchema.amount` gained an int64-ceiling `.refine` — see Gotchas)

## Purpose

The `payments` module is `POST /payments`: it builds an unsigned classic Stellar payment transaction (merchant is the source, live sequence number from Horizon) sending a registry asset to any destination, and stores it as a pending `'payment'`-kind `intents` row alongside a pending `'send'` `activity` row. It does not submit anything — completion (co-signing via Privy `rawSign`, sponsor fee-bump, actual submission) is entirely the `intents` module's concern (`POST /intents/:id/complete`, `docs/modules/api-intents.md`), which this module's intents feed straight into unmodified. It is a sibling of `wallet`/`intents`, not a dependency of either — it queries `merchants`/`intents`/`activity` directly via its own narrow `PaymentsRepo`, the same decoupled-siblings pattern `intents` already established (`docs/modules/api-intents.md`'s Gotchas).

## Endpoints / Public surface

Registered inside `app.ts`'s authenticated scope (`api/src/app.ts:93-99`) — requires `Authorization: Bearer <Privy access token>` (see `docs/modules/api-auth.md`) and reads `request.privyDid`.

| Method | Path | Body | Response | Notes |
|---|---|---|---|---|
| `POST` | `/payments` | `PaymentRequest` — `{destination: string, amount: string, assetCode: string}` | `200 PaymentResponse` — `{intentId, xdr, hashHex}` | The returned `xdr` is **unsigned** — the merchant must co-sign via Privy `rawSign` and submit through `POST /intents/:id/complete`, which wraps it in a sponsor-paid fee-bump. |

### Error responses

| Condition | Status | Body | Notes |
|---|---|---|---|
| Body fails `PaymentRequestSchema` (bad `destination` shape, `amount` not a positive ≤7dp decimal string ≤ Stellar's int64 maximum, empty `assetCode`) | 400 | `{code: 'invalid_request', details: {issues}}` | Checked entirely in `routes.ts` via `safeParse` — never reaches the service (see Gotchas for why `safeParse`, not `.parse()`, is required here). |
| `destination` is shape-valid (passes the regex) but its embedded checksum is invalid | 400 | `{code: 'invalid_request'}` | Checked first in `createPayment` via `StrKey.isValidEd25519PublicKey` — the schema regex alone can't catch this (see Gotchas). |
| `assetCode` is shape-valid but not in `TESTNET_REGISTRY` | 400 | `{code: 'unknown_asset'}` | Checked first in `createPayment`, before any DB/Horizon access. |
| No `merchants` row for the caller | 404 | `{code: 'merchant_not_found'}` | Mirrors `wallet.getWallet`'s same code — call `POST /wallet/provision` first. |
| `destination` equals the caller's own `stellarAddress` | 400 | `{code: 'self_payment'}` | Checked after the merchant row is resolved (need to know the merchant's own address). |
| Merchant's Stellar account does not exist on-chain yet (provisioning intent still pending/unsubmitted) | 409 | `{code: 'merchant_not_provisioned'}` | `stellarGateway.loadAccount` rejects with `StellarAccountNotFoundError`; translated here rather than left to escape as a generic 500. |
| Any other `loadAccount` failure (Horizon outage, network error) | 500 | `{code: 'internal_error'}` | Rethrown unchanged — not masked as `merchant_not_provisioned`. |
| Destination has no trustline for the asset | *(not checked here)* | — | Not validated at creation — Horizon rejects it at submission time (`op_no_trust`); surfaces through `POST /intents/:id/complete`'s `submission_failed` response as `reason: 'tx_failed:op_no_trust'` (`docs/modules/api-sponsor.md`'s `sanitizedReason`). |

## Gotchas & invariants

- **A completed payment now produces exactly ONE activity row, not two — this required a coordinated change to `intents/service.ts`, made as part of this same change.** Before this change, `intents/service.ts`'s `recordActivity` unconditionally INSERTed; if this module also wrote a pending row at creation, a confirmed/failed payment would end up with a permanent pending+confirmed (or pending+failed) double row for the same payment, with no reconciliation. The fix: this module's `recordPendingActivity` tags its row with `externalRef` = the created intent's id (`service.ts:69`, matching `activity.externalRef`, `db/schema.ts`), and `intents/service.ts`'s `createDrizzleIntentsRepo.recordActivity` now does upsert-by-`externalRef` — UPDATE the matching row's `status`/`txHash` in place if one exists, INSERT only if none does (`api/src/modules/intents/service.ts` — see `docs/modules/api-intents.md`'s Gotchas for the full mechanism and its own test coverage). `provision`-kind intents are unaffected: `wallet/service.ts`'s `provision()` never writes a pending activity row, so their completion `recordActivity` call still always inserts, exactly as before.
- **`safeParse`, not `.parse()`, in `routes.ts` — this was the first route in this codebase to validate a request body against client input, and it surfaced a genuine pre-existing gap that `intents/routes.ts` has since also closed.** A thrown `ZodError` is NOT an `AppError` — `app.ts`'s global error handler (`api/src/app.ts:101-115`) would map it to a generic `500 {code: 'internal_error'}`, not a 400. This module's spec explicitly requires 400s for bad `destination`/`amount`/`assetCode`, so `routes.ts` catches the failure locally via `.safeParse` and rethrows as `AppError('invalid_request', ..., 400, {issues})` (`routes.ts:27-30`). At the time this was written, `intents/routes.ts`'s `CompleteIntentRequestSchema.parse(request.body)` still had the same gap unaddressed (a missing `signature` field was a client bug with no automated test for it) — a later fix wave closed it there too, switching to the same `safeParse` shape (see `docs/modules/api-intents.md`'s Gotchas).
- **Trustline-missing destinations are NOT checked at creation — they fail at submission (`op_no_trust`), and the failure reason is now specific.** As part of this same change, `sponsor/submit.ts`'s failure sanitizer was extended: previously a Horizon `tx_failed` transaction-level code (the generic "one of the operations failed" result) was returned as the bare string `'tx_failed'`, dropping Horizon's more specific per-operation `result_codes.operations` codes entirely. `sanitizedReason` (`api/src/modules/sponsor/submit.ts`) now appends the first non-`'op_success'` operation code when the transaction code is `'tx_failed'`, e.g. `reason: 'tx_failed:op_no_trust'` for a payment to a destination with no trustline — this is what a payment intent's `POST /intents/:id/complete` call returns in `submission_failed`'s `details.reason` (`docs/modules/api-intents.md`'s error table) when the destination lacks the asset's trustline. See `docs/modules/api-sponsor.md`'s Gotchas for the full mechanism and its tests.
- **`merchant_not_provisioned` (409) is a deliberate addition beyond the spec's explicit edge-case list** — `stellarGateway.loadAccount(merchant.stellarAddress)` is needed for the tx's live sequence number, and a merchant whose provisioning intent is still pending has no on-chain account yet, so `loadAccount` rejects with `StellarAccountNotFoundError`. Left uncaught, that would escape as an unlabeled generic 500 (the same shape as a real Horizon outage) — translating it into a distinct, actionable 409 costs one `instanceof` check and matches this module's overall pattern of specific codes for specific rejections. Any OTHER `loadAccount` failure (a real outage) is rethrown unchanged, not masked — same rationale as `wallet/service.ts`'s `getWallet` (`docs/modules/api-wallet.md`'s Gotchas).
- **`destination`'s checksum is validated in `service.ts`, not just its shape in `PaymentRequestSchema` (fix-wave addition, `service.ts:122-130`).** The shared schema's regex (`/^G[A-Z2-7]{55}$/`) only checks that a string LOOKS like a Stellar G-address — it can't validate the embedded CRC16 checksum, so a shape-valid-but-corrupted address (e.g. one character flipped) would pass the schema and reach `Operation.payment` in `service.ts`, which throws a raw, non-`AppError` error that `app.ts`'s handler would map to a generic 500. `StrKey.isValidEd25519PublicKey(request.destination)` closes this — checked right after the registry lookup and before any DB/Horizon access, throwing `AppError('invalid_request', ..., 400)` on failure. Tested with a real keypair's address with its last character (part of the checksum) flipped to a different valid base32 char — same length, same regex match, invalid checksum.
- **`self_payment` is checked AFTER the merchant lookup, not before** — it inherently needs to know the caller's own `stellarAddress` to compare against `request.destination`, so `repo.getMerchant` must resolve first. This means an unprovisioned caller gets `merchant_not_found` (404) rather than a self-payment check on a nonexistent address, which is the only sensible order.
- **No live-Postgres integration test exists for this module** (nor for `wallet`/`intents`) — `service.test.ts` uses fakes exclusively; `routes.test.ts`'s REAL-`buildApp` tests are deliberately limited to paths that never touch the DB (401 unauthorized; the `invalid_request`/`unknown_asset` 400s, both of which throw before `repo.getMerchant` is ever called) — consistent with the rest of this codebase's testing convention (`docs/modules/api-wallet.md`/`docs/modules/api-intents.md`'s Testing sections). A true `self_payment`/happy-path assertion through the real authenticated HTTP surface would require a working fake or live `NodePgDatabase`, which no test in this repo currently sets up.
- **`PaymentResponseSchema` duplicates `ProvisionPendingSchema`'s exact shape** (`{intentId, xdr, hashHex}`) rather than reusing it — each endpoint's response contract is independently defined throughout `packages/shared/src/api.ts` (see `shared.md`), so this follows the established pattern rather than introducing a shared alias two modules would then both depend on.

## Testing

- `api/src/modules/payments/service.test.ts` (7 tests, up from 6 — the fix-wave `StrKey` checksum check added the last 1): happy path — builds an unsigned tx (`tx.signatures` empty, `tx.source === merchant.publicKey()`, `fee: '100'`, a single `payment` operation with the exact destination/amount/asset), stores it as a `'payment'`-kind intent, and records a pending `'send'` activity row with the full payment detail (`counterparty`/`amount`/`assetCode`/`assetIssuer`); **`invalid_request` 400 for a shape-valid but bad-checksum `destination`** (a real address with its last character flipped); `unknown_asset` 400 for an assetCode not in the registry; `merchant_not_found` 404 for an unprovisioned caller; `self_payment` 400 for `destination === merchant.stellarAddress`; `merchant_not_provisioned` 409 when the merchant's account doesn't exist on-chain yet; a non-"not found" gateway failure rethrows unchanged (not masked). Fake `PaymentsRepo`/`StellarGateway` defined in the test file — no live Postgres/Horizon, mirroring `wallet/service.test.ts`'s fake shapes exactly.
- `api/src/modules/payments/routes.test.ts` (7 tests): two standalone-plugin tests (`paymentRoutes` on a bare Fastify instance, `request.privyDid` stubbed via a test-only hook, fake `PaymentsService`) — happy path passes the parsed body through to the service and returns its result; an invalid body (bad `destination`) 400s without ever calling the service. Five REAL-`buildApp` tests: `401 {code: 'unauthorized'}` with no `Authorization` header; an invalid `destination` → `400 {code: 'invalid_request'}`; an amount with more than 7 decimal places → `400 {code: 'invalid_request'}`; a zero amount → `400 {code: 'invalid_request'}`; an assetCode not in `TESTNET_REGISTRY` → `400 {code: 'unknown_asset'}` — all four buildApp validation tests use fakes that throw if `loadAccount`/`submitTransaction`/DB access is ever attempted, asserting these failures are caught before any I/O.
