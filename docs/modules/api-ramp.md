## Purpose

The `ramp` module talks to Etherfuse, the fiat on/off-ramp provider: it onboards a merchant (organization creation, hosted-KYC launch, BRL/PIX bank account + Stellar wallet registration), and quotes/executes BRL-over-PIX transfers in BOTH directions — on-ramp deposits (payin) and anchor-mode off-ramp withdrawals (payout). At the PROVIDER layer (`provider.ts`/`etherfuse.ts`) it follows the same "provider builds/fetches data, caller signs/submits" split as `vault`/`sponsor` — `etherfuse.ts` never signs or submits a Stellar transaction. The service + HTTP layers sit on top: `service.ts`'s `RampService` drives the onboarding state machine against a `ramp_customers` Postgres row (`api/src/db/schema.ts:113-121`), the payin order lifecycle against `activity` rows, and the payout lifecycle against BOTH an `intents` row (the merchant-signed payment) and an `activity` row — and `routes.ts`'s `rampRoutes` exposes all of it — mirroring `vault/service.ts` + `vault/routes.ts`'s layering over `vault/provider.ts` (see `docs/modules/api-vault.md`).

Every path/body/response mapping in this module is evidence-backed against a real Etherfuse sandbox run — see `docs/evidence/etherfuse-sandbox-findings.md`, produced by the manually-run `api/scripts/spike-etherfuse.ts` (`pnpm --filter @paltalabs/api spike:etherfuse`).

## Endpoints / Public surface

**This module's own HTTP surface** (all under the authenticated scope, `api/src/app.ts:172-180` — see `docs/modules/api-auth.md`). Every request-body parse failure is 400 `invalid_request`; every `RampProviderError` is 502 `ramp_provider_error` with the provider's sanitized `{reason}`.

|---|---|---|---|---|
| `GET` | `/ramp/onboarding` | — | `RampOnboardingStatusSchema` (`{status: 'not_started' \| 'verifying' \| 'incomplete' \| 'ready'}`) | No merchant-existence check — a caller with no `merchants` row also has no `ramp_customers` row (FK), so it naturally reads `not_started` (`service.ts:465-476`). `verifying`/`incomplete` cost one live `getKycStatus` call; `ready` costs none — see Gotchas. |

| `POST` | `/ramp/payout` | `PayoutExecuteRequestSchema` (`{quoteId, amountCents}`) | `PayoutIntentResponseSchema` (`{intentId, xdr, hashHex}`) | 409 `ramp_not_onboarded`; 502 `ramp_provider_error` (`reason: 'order_rejected'`) on a stale quote, a duplicate open order, or an anchor memo that doesn't decode to 32 bytes. See Gotchas for the full anchor-mode/amount/reconciliation rationale. |

## Gotchas & invariants

- **The API key goes in `Authorization` RAW — a `Bearer ` prefix is Etherfuse's documented #1 cause of 401** (`etherfuse.ts:249`, `docs/evidence/etherfuse-sandbox-findings.md`'s header note). The key is never logged and never asserted into a snapshot: `etherfuse.test.ts`'s `expectAuthHeader` compares it against a local fixture constant with `toBe`, so a real key can never leak into a committed snapshot file.
- **The launch JWT MUST be RS256 — ES256 is rejected outright**, with `invalid_client` / ``Disallowed signature algorithm: algorithm `ES256` is not one of: RS256`` (`docs/evidence/etherfuse-sandbox-findings.md` "## Launch JWT", Conclusions §4). It is signed with `node:crypto` alone (`etherfuse.ts:307-343`), which is why `buildKycLaunch` can stay synchronous and why this module has **no JWT-library dependency**. Two dashboard-side preconditions are equally load-bearing: `ETHERFUSE_JWT_ISSUER` must equal the registered Issuer URL, `ETHERFUSE_JWT_KID` must match a key in the registered JWKS, and **that JWKS URL must serve `Content-Type: application/json`** (a `text/plain` response — e.g. a raw gist — is rejected). Etherfuse re-fetches the JWKS on every verification.
- **`email` and `name` are REQUIRED JWT claims, and Etherfuse offers no way to read a personal organization's email back** — so `POST /ramp/onboarding/kyc-launch` takes a body (`{displayName, email}`) instead of none, and re-sends them on every launch (`routes.ts:52-65`, `service.ts:445-448`). The claim is informational: the address the hosted `/idv` flow actually confirms is the one the organization was created with, so a client that lies here only affects its own session. That org email **must be a real, receivable inbox** — the `email_confirmation` requirement emails a real PIN even in sandbox (`docs/evidence/etherfuse-sandbox-findings.md` Conclusions §6).
- **`claimOwnership: true` is mandatory on wallet registration** (`etherfuse.ts:358-370`). Without it the wallet's own `kycStatus` stays `not_started` even after the organization is approved, and every order 400s with `"Terms and conditions have not been completed for the selected wallet"` (`docs/evidence/etherfuse-sandbox-findings.md` "## Wallet registration", Conclusions §5).
- **The BRL bank-account body nests under `account`** — the flat shape is not accepted (`etherfuse.ts:345-355`, `docs/evidence/etherfuse-sandbox-findings.md` "## Bank account (BRL/PIX)"). Two hard provider rules follow from that same section: registration is **gated on KYC approval** (409 `"Organization must be approved before adding a bank account"` — this module pre-empts it with its own 409 `kyc_not_approved`), and **only ONE BRL bank account is allowed per organization**, which is exactly why `completeSetup` skips the step whenever `bankAccountId` is already persisted. Only `pixKeyType: 'email'` is live-verified; the other values `PixDetailsRequestSchema` allows (`cpf`/`phone`/`evp`) rely on Etherfuse's own rejection.
- **`POST /ramp/order`'s response carries ONLY the deposit block — no status and no settlement amount — so the CLIENT echoes its own quote's amount rather than this module deriving one via a read-back.** `createOnrampOrder` (`etherfuse.ts:389-409`) maps ONLY that create response; `provider.ts`'s `OnrampOrderState` (`provider.ts:71-74`) is therefore just `{orderId, deposit}` — no `status` (implicitly `created`, Etherfuse's own initial order state) and no `receiverAmountCents`. `POST /ramp/payin`'s request body is `PayinExecuteRequestSchema` (`@paltalabs/shared`, `{quoteId, amountCents}`) — the client re-sends the `receiverAmountCents` from the SAME quote it already holds (from a prior `POST /ramp/payin/quote`), and `createPayin` (`service.ts:583-620`) writes that value straight onto the pending `activity` row (`centsToDecimal(request.amountCents)`) and echoes it back verbatim as the response's `receiverAmountCents`, with no re-derivation anywhere. This mirrors the trust envelope the payout flow's `{quoteId, amountCents}` design already relies on: Etherfuse validates the actual token delivery against the quote on its own side, so a client that lies about `amountCents` here only mislabels its own merchant's `activity` row — it can never change what actually settles.
  **An earlier version of this module instead read the order back with a second `GET /ramp/order/{id}` call** to derive the amount from `amountInFiat × exchangeRate` (`amountInTokens` only appears once an order **completes** — `docs/evidence/etherfuse-sandbox-findings.md` "## Onramp order & deposit payload" and "## Fiat received & settlement"). That design was rejected in review for two reasons: (a) it rested on a read-back payload that had not yet been committed as evidence, and (b) a read-back failure after a successful create left the order **permanently stranded** — no `activity` row meant every ownership check (`getPayinState`/`simulatePayin`) 404'd forever, and Etherfuse's duplicate-open-order 409 blocked the merchant's immediate retry. `deriveTokenCents` and the `decimalProductToCents` helper it needed are both deleted; `decimalToCents` (still used by quote mapping) is unaffected.
- **Any response-mapping failure — not just a non-2xx HTTP status — surfaces as `RampProviderError` with the SAME `reason` token the method's HTTP failures use.** `mapResponse` (`etherfuse.ts:211-218`) wraps `createQuote`'s call to `toRampQuote`, so a garbage decimal string (`parseDecimal` throws a plain `Error` on anything not matching `/^\d+(\.\d*)?$/`) 502s as `quote_rejected`, exactly like a rejected HTTP quote request would — matching `RampProviderError`'s own doc comment ("Thrown ... on a non-2xx provider response OR malformed provider data", `provider.ts:117`). `createOnrampOrder`'s mapping is now trivial field renaming with nothing left to parse, so it needs no such wrapper.
- **A `denied` KYC status has no distinct onboarding state — it surfaces as `verifying`, the same bucket as `in_progress`/`submitted`.** `RampOnboardingStatusSchema` (`@paltalabs/shared`) is a 4-state enum (`not_started`/`verifying`/`incomplete`/`ready`) with no `denied` member; `onboardingStatus` (`service.ts:465-476`) only branches on `kycStatus !== 'approved'` → `verifying`, so a merchant whose hosted `/idv` run was actually rejected reads back identically to one still mid-flow. The recovery path is the SAME one any `verifying` merchant uses: `POST /ramp/onboarding/kyc-launch` re-issues fresh launch parameters for another `/idv` attempt — there is no separate "denied" affordance, and none is needed, since Etherfuse's hosted flow is where a merchant actually retries a denied verification.
- **Decimal amounts are converted with exact integer math, never floats.** Etherfuse returns 27-fractional-digit strings (`"19.620062792064687229069147940"`); `parseDecimal`/`scaleToCents` (`etherfuse.ts:140,148`) work in BigInt. The rounding modes are a deliberate asymmetry: **receiver amounts floor** (never promise the merchant more than gets delivered) and **fees ceil** (never understate what is charged) (`etherfuse.ts:185-197`). `commercialQuotation` is the one lossy field — a `Number(exchangeRate)` for display only.
- **Ownership of an order is resolved ONLY against our own `activity` row.** `GET /ramp/order/{id}`'s `customerId` is the PARTNER organization's id, not the merchant's (a side effect of `claimOwnership`), so it can never answer "whose order is this?" (`docs/evidence/etherfuse-sandbox-findings.md` Conclusions §10). `requireOwnedOrder` (`service.ts:456-462`) matches `externalRef: 'order:<orderId>'` against the caller's own `stellarAddress`, and `provider.getOrder`'s echoed `orderId` is never used as an authorization input.
- **`txHash` is nullable end-to-end and must stay that way.** A completed ON-ramp order carries no `confirmedTxSignature` at all in sandbox — the delivery `path_payment` is only visible on Horizon — and an OFF-ramp order's `confirmedTxSignature` is an Etherfuse-internal transaction, NOT the merchant's payment (`docs/evidence/etherfuse-sandbox-findings.md` Conclusions §9). `getOrder` maps `confirmedTxSignature ?? null` and never throws on its absence (`etherfuse.ts:435-442`). `OrderState.amountTokens` (added for Task 6) is nullable for the SAME reason, but on a different axis: it's absent on every order status except `'completed'` (not "never present in sandbox" like an off-ramp `txHash` effectively is) — `getOrder` maps `amountInTokens ?? null` identically (`etherfuse.ts:437-446`).
- **There is no PIX copy-paste code and no QR payload in the sandbox.** The BRL deposit response reuses the CLABE-shaped body with an always-empty `depositClabe` (dropped at the boundary) and `depositBankName: "PIX"`; the order READ even reports `depositBankName: "STP"`, an MXN rail label. The only user-facing deposit reference is the amount plus Etherfuse's hosted status page (`https://<dashboard>/ramp/order/<orderId>`). **Do not design a PIX-code/QR panel around sandbox data** — revisit against production payloads before mainnet (`docs/evidence/etherfuse-sandbox-findings.md` Conclusions §8).
- **Quotes expire in 2 minutes, and expiry is Etherfuse's concern, not this module's.** No local TTL is duplicated (same stance as the previous provider): a stale `quoteId` surfaces as an ordinary 502 `order_rejected` from `createPayin`. The UI is expected to count down from the quote's `expiresAt`.
- **Every id we send is generated server-side — never client-supplied.** `customerId` (`service.ts:503`), `orderId` (`service.ts:590` for `createPayin`, `service.ts:665` for `createPayout` — both directions), the bank account's `transactionId` (`service.ts:541`), and `quoteId` (`etherfuse.ts:273`) are all `randomUUID()`. The organization id doubles as the `customerId` everywhere and re-POSTing it is idempotent; `transactionId` is Etherfuse's idempotency key.
- **The onboarding ladder has four states, derived (never stored) from `ramp_customers` + one live KYC read.** `ready` short-circuits BEFORE the provider call (`service.ts:465-476`): both ids being set implies KYC was approved earlier (it gates registration), so the most-polled endpoint in the module costs zero provider round-trips once a merchant is live. Only `verifying`/`incomplete` pay for a `getKycStatus` call.
- **`POST /ramp/onboarding/start` is idempotent by design, not by an idempotency key — and two genuinely CONCURRENT calls leave an accepted orphan.** If both read no row, both create an Etherfuse organization; `insertRampCustomer`'s `ON CONFLICT DO NOTHING` means only the first persists, and the loser re-reads the row and builds its launch against the WINNER's `customerId` (`service.ts:491-510`). The loser's own organization is abandoned — harmless, never referenced again. Preventing it would need cross-request locking (e.g. a Postgres advisory lock keyed by `privyDid`), deliberately not implemented; the trade-off is pinned by `service.test.ts`'s losing-concurrent-call case.
- **`POST /ramp/onboarding` is resumable per field.** Each of bank-account/wallet registration runs only when its id is still unset and persists before the next starts (`service.ts:532-559`), so a retry after a mid-flight provider failure resumes at the first missing piece. This matters more than it did with the previous provider: re-running the bank step would hit Etherfuse's one-BRL-account-per-organization rule and hard-fail.
- **`POST /ramp/payin/:orderId/simulate` is testnet-only and 404s (not 403s) on mainnet, before any DB lookup** (`service.ts:628-637`). The simulator only exists in Etherfuse's sandbox; on mainnet the route must be indistinguishable from one that was never registered.
- **UPDATED (Task 6): a payin's pending `on_ramp` activity row IS now reconciled — `indexer/ramp-poller.ts`'s `createRampPoller` re-checks it against `provider.getOrder` every `POLL_INTERVAL_MS` cycle and confirms/fails it once Etherfuse reports a terminal order status.** Full detail (including a permanent-duplicate-row gap for the sandbox's null-`confirmedTxSignature` case) is in `docs/modules/api-indexer.md`'s Gotchas. `GET /ramp/payin/:orderId` remains available for a merchant to poll directly regardless.
- **`POST /ramp/payout`'s request body re-sends the amount, exactly like payin, but the payout side's trust backstop is Etherfuse's own auto-refund, not just its server-side quote validation.** `PayoutExecuteRequestSchema` (`@paltalabs/shared`, `{quoteId, amountCents}`) mirrors `PayinExecuteRequestSchema` — the client echoes the SAME quote's own sender-side amount rather than this service re-deriving it, because `provider.createAnchorOfframpOrder`'s response carries no settlement amount either (`OfframpAnchorDetails`, `provider.ts:97`). `docs/evidence/etherfuse-sandbox-findings.md`'s `## Anchor order`/`## Anchor payment & completion` sections establish the backstop: Etherfuse validates the on-chain payment against the order and AUTO-REFUNDS a mismatch, so a client that lies about `amountCents` here only gets its own payment refunded — it can never cause a different amount to actually settle. See `createPayout`'s doc comment (`service.ts:659-733`).
- **The anchor order's memo MUST decode to exactly 32 bytes, checked BEFORE the merchant is ever asked to sign anything.** `Memo.hash` requires a fixed 32-byte value (live-verified: the sandbox's `withdrawMemo` — e.g. `"2j2eY+8NQxyVF8GhRcECewAAAAAAAAAAAAAAAAAAAAA="` — always decodes to exactly 32 bytes, `docs/evidence/etherfuse-sandbox-findings.md`'s `## Anchor order` section). `createPayout` guards `Buffer.from(details.withdrawMemoBase64, 'base64').length !== 32` and fails closed with a 502 `ramp_provider_error` (`reason: 'order_rejected'`) rather than building and returning a payment whose memo Etherfuse can never match — a wrong memo just gets auto-refunded (same backstop as above) after burning a whole merchant-signing round-trip, so failing before that round-trip starts is strictly cheaper. Covered by a dedicated `service.test.ts` case.
- **`createPayout` builds the Stellar payment itself — Etherfuse's anchor mode returns no unsigned transaction.** Etherfuse's `createAnchorOfframpOrder` hands back only `{withdrawAnchorAccount, withdrawMemoBase64}` — an account and a memo, nothing signable. So `createPayout` is the one place in this module that builds a `TransactionBuilder` chain (`Asset`/`BASE_FEE`/`Memo`/`Operation`, `service.ts:16`), sourced by the merchant's own live account (`gateway.loadAccount`) and left deliberately UNSIGNED — the merchant co-signs via Privy `rawSign` before `POST /intents/:id/complete`, the exact same contract `payments/service.ts`'s `createPayment` uses.
- **The submitter needs no `RampProvider` at all.** `createPayoutSubmitter` (`./submitter.ts:47`) only fee-bumps the merchant-signed inner tx (`wrapFeeBump`) and calls `gateway.submitTransaction(built)` — classic Horizon, the same gateway `createPaymentSubmitter` uses. This is possible BECAUSE `createPayout` already resolved everything Etherfuse-specific (the anchor account, the memo) at INTENT-CREATION time; by completion time, the merchant's signed payment tx IS the entire off-ramp withdrawal — there is nothing left to ask Etherfuse for. `submit`'s failure mapping is deliberately flat (`SubmissionFailedError('submission_failed')` for ANY gateway rejection) rather than reusing `sponsor/submit.ts`'s Horizon-`result_codes`-parsing `submitAndClassify` (module-private, not exported) — a stale-sequence payout submission surfaces as a generic 502 instead of the dedicated `intent_expired` 409 other submitters get.
- **A payout's `off_ramp` activity row is NOT confirmed by the signing-flow completion itself — `intents/service.ts`'s Horizon-payments INDEXER confirms it independently, the same way it confirms every other pending row.** `createPayout`'s `recordPendingPayoutActivity` call (`service.ts:723-730`) tags its pending row `externalRef: 'order:<orderId>'` — the SAME convention `createPayin`'s `on_ramp` row and `requireOwnedOrder`'s ownership lookup use, keyed off the LOCALLY-generated `orderId` (never the provider-echoed `details.orderId` — nothing guarantees Etherfuse echoes back exactly what was sent) — AND stamps the identical value onto the intent's own `metadata.activityExternalRef` (`service.ts:712-717`; a single `activityExternalRef` local is computed once, `service.ts:710`, and reused for both so they can never drift). `intents/service.ts`'s `complete()` reads that field as a GENERIC, kind-agnostic signal (see `docs/modules/api-intents.md`'s Gotchas for the full contract): on a successful submission it writes ONLY the real fee-bump `txHash` onto that exact row (`repo.updateActivityTxHash`) and leaves `status: 'pending'` untouched; on a failed submission it flips that SAME row to `'failed'` (keyed by `activityExternalRef`, not the intent's own id) instead of inserting an unrelated second row. **Why leave it pending at all**: `indexer/poller.ts`'s Horizon-payments poller ALREADY confirms this exact row the moment it next polls and sees the matching outgoing payment — `RAMP_OWNER_TYPE`'s cross-type dedupe check (`poller.ts:218-227`) matches a normalized `'send'` record against a pending `'off_ramp'` sibling by `(txHash, stellarAddress)` and confirms it there; `intents/service.ts`'s completion flow deliberately does NOT duplicate that confirmation. This is also why the PRE-submission crash-window write (which happens before `submit()` is even called, closing the window where a process crash between Horizon accepting the tx and the post-submit write would otherwise leave `txHash: null` forever) must ALSO use `activityExternalRef`, not `claimed.id` — a `txHash: null` row is exactly what the indexer's cross-type dedupe can never match, producing a duplicate `'send'` row instead of confirming this one (`docs/modules/api-intents.md`'s Gotchas has the full crash-window rationale — this was itself a same-day fix). This closes a real defect an earlier revision of this task shipped: without `activityExternalRef` at all, `complete()`'s hardcoded `externalRef: claimed.id` could never match the pending `'order:<orderId>'` row, so a completed payout silently inserted a SECOND, orphaned `off_ramp` row instead of updating the pending one — caught and fixed same-day (`docs/modules/api-intents.md`'s Testing section). What a genuinely FUTURE order-status reconciler (not built in this task) is actually needed for is narrower than "confirm the row" — see the next two bullets.
- **The offramp order's `confirmedTxSignature` (from `provider.getOrder`) is NEVER the merchant's own payment hash — it is Etherfuse-internal** (`docs/evidence/etherfuse-sandbox-findings.md`'s `## Anchor payment & completion` section: the merchant's own submitted tx hash and the order's `confirmedTxSignature` were live-verified to be two DIFFERENT values). Nothing in this module — or in `intents/service.ts`'s completion flow, or `indexer/poller.ts`'s Horizon-based confirmation (the bullet above) — ever writes an activity row's `txHash` from provider (Etherfuse) data; it is always either the merchant's own precomputed fee-bump hash or Horizon's own reported hash for that exact submission. **UPDATED (Task 6): the order-status reconciler this invariant was written for (next bullet) is now built** — `indexer/ramp-poller.ts`'s `RampPollerRepo.confirmOffRamp` (`ramp-poller.ts:67-75`) takes no `txHash`/`amount` argument at all, structurally preserving this rule (a future caller cannot even accidentally pass one) — see `docs/modules/api-indexer.md`'s Gotchas.
- **A payout order can sit at `funded` for a long time before `completed`/`finalized` — sandbox lifecycle honesty.** `docs/evidence/etherfuse-sandbox-findings.md`'s `## Anchor payment & completion` section: after the merchant's payment is detected on-chain (~25s), the order flips to `funded`, but was still `funded` — no `completedAt`, no `trackingCode` — ten minutes later when that recording session ended; the sandbox's BRL fiat leg settles asynchronously (or not at all without operator action). **UPDATED (Task 6) — PARTIALLY closed, split into two halves:** (1) a payout row still `'pending'` when a genuinely different fiat-side outcome arrives — Etherfuse refunds/cancels the anchor order before the on-chain leg the indexer confirms ever lands — IS now caught: `indexer/ramp-poller.ts`'s poller re-checks every still-`'pending'` `'off_ramp'` row against `provider.getOrder` each cycle and marks it `'failed'` on `refunded`/`canceled` (`docs/modules/api-indexer.md`'s Purpose/Gotchas). (2) **STILL a genuinely future gap, NOT built by Task 6**: correcting a row the Horizon poller ALREADY flipped to `'confirmed'` (the on-chain payment landed) if Etherfuse's fiat-side processing SUBSEQUENTLY fails/refunds/cancels the order — `indexer/ramp-poller.ts`'s own query only ever selects still-`'pending'` rows (`RampPollerRepo.listPendingOrderActivity`, `WHERE status = 'pending'`), so an already-`'confirmed'` row is invisible to it and stays wrongly marked `'confirmed'` on-chain while the merchant never actually received their BRL, with no automated pass to notice or correct it (per `docs/evidence/etherfuse-sandbox-findings.md`, which recorded only the success path — this failure mode has not been independently re-verified live). Any payout UX built on top of this module must show progress (e.g. `funded` = "payment received, payout processing") and must NOT promise same-session completion, mirroring the payin module's existing `## Fiat received & settlement` gotcha for the on-ramp direction.
- **Nothing in this module signs or submits a Stellar transaction OUTSIDE of `createPayout`/`createPayoutSubmitter`, and every `IntentKind` now has a registered submitter.** `app.ts`'s `submitters` map (`api/src/app.ts:100-106`) registers `payout: createPayoutSubmitter(deps.sponsorKeypair, deps.stellarGateway)` alongside the pre-existing four — see `docs/modules/api-intents.md`.
