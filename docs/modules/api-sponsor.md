# api-sponsor Module

> **Living document.** Read this before modifying the module. Update it in the same change whenever the module's behavior, exports, files, or dependencies change.

**Source:** `api/src/modules/sponsor/` · **Last verified:** 2026-08-03 (Prior change (2026-07-24): added a third submitter factory, `createSorobanSubmitter` — produces the `'vault_deposit'`/`'vault_withdraw'`-kind `IntentSubmitter`s for the `vault` module, submitting through `SorobanGateway.sendAndConfirm` instead of Horizon; see Structure, Key methods, Gotchas, Testing)

## Purpose

The `sponsor` module provides the Stellar signing toolkit for the wallet's signing pattern. It bridges Privy's ed25519 `rawSign` capability (which returns a raw 0x-hex signature) with Stellar SDK's transaction signing and fee-bump pattern, enabling merchant accounts (holding zero XLM) to submit transactions sponsored by the server's sponsor account. This is the crypto core of the transaction flow: merchant signs the inner transaction via Privy, server wraps it in a fee-bump and signs as sponsor. It also owns the final step of that flow — actually submitting a merchant-signed transaction to Stellar and classifying the result (`submit.ts`). This module owns EVERY generic `IntentSubmitter` factory regardless of which feature module's intents they submit (`'provision'`/`'payment'` for `wallet`/`payments`, `'vault_deposit'`/`'vault_withdraw'` for `vault`) — a submitter is "generic" in the sense that its own logic (fee-bump-or-not, which gateway, how to classify a failure) has nothing feature-specific baked in; only a later payout submitter with genuinely provider-specific logic (a payment-rail callout, not just Stellar/Soroban submission) would move out of this module.

## Dependencies

- `@stellar/stellar-sdk` — Stellar SDK (`api/package.json:13`). Imported types: `Transaction`, `FeeBumpTransaction`, `Keypair`, `TransactionBuilder`.
- `../../lib/stellar-gateway.ts` (`StellarGateway`) — `submitAndClassify` calls `gateway.submitTransaction`; it does not construct a gateway itself.
- `../../lib/soroban-gateway.ts` (`SorobanGateway`, `SorobanSubmissionError`) — `submitAndClassifySoroban`/`createSorobanSubmitter` call `gateway.sendAndConfirm` and classify its rejection; added alongside `createSorobanSubmitter`, unused by the two Horizon-backed factories.
- `../intents/service.ts` (`type IntentSubmitter`, type-only) — every factory's return type. This is a circular import at the type level (`intents/service.ts` imports `StaleSequenceError`/`SubmissionFailedError` from `submit.ts`, `submit.ts` imports `IntentSubmitter`'s type from `intents/service.ts`) — safe because it's `import type` on this side, erased entirely at build time, so there is no runtime circular dependency between the two modules.
- **No other external dependencies beyond stellar-sdk.**

## Gotchas & invariants

- `txHashHex` returns the transaction ID/hash (the SHA-256 of the network-bound signature base), which is the preimage Privy's `rawSign` operates on and matches what Horizon reports for the confirmed tx.
- `attachRawSignature` expects a 0x-prefixed hex string (Privy's output format). It strips the prefix, converts to Buffer, then encodes as base64 for stellar-sdk's `addSignature`.
- `attachRawSignature` validates the signature against the tx hash internally (via `addSignature`); invalid signatures throw and never attach. This means you do not need separate validation before calling it.
- Merchant accounts are assumed to hold zero XLM. The `wrapFeeBump` always signs as sponsor and is meant to be the only signature on the fee-bump; the inner tx must already be signed by the merchant before wrapping.
- `baseFee` is per operation; the fee-bump's total fee is `baseFee * (inner tx operation count + 1)` (the +1 is for the fee-bump itself).
- **`wrapFeeBump`'s default `baseFee` (`'10000'`) is too low for Soroban invoke legs.** stellar-sdk's `TransactionBuilder.buildFeeBumpTransaction` (which `wrapFeeBump` calls) requires `baseFee >= (inner tx fee − Soroban resource fee) / inner tx operation count` — i.e. the inner tx's *inclusion* fee per operation, resource fee excluded. An `rpc.assembleTransaction`-assembled Soroban invoke tx typically carries a large inclusion fee (the draft's chosen `TransactionBuilder` fee, before the resource fee is added on top), so wrapping it needs an explicit `baseFee` argument matching or exceeding that draft fee — confirmed live on testnet in the Privy×Stellar testnet spike (`api/scripts/spike-privy-stellar.ts:216,231`, evidence in `docs/evidence/privy-stellar-spike.md`), where the default threw `"Invalid baseFee, it should be at least 1000000 stroops."` until `wrapFeeBump(sponsor, invokeTx, '1000000')` was passed explicitly.
- **FINDING (installed `@stellar/stellar-sdk@14.6.1`): `Horizon.Server#submitTransaction`'s own `.catch` handler always re-rejects the raw Axios error UNCHANGED.** Read directly from `node_modules/.pnpm/@stellar+stellar-sdk@14.6.1/node_modules/@stellar/stellar-sdk/lib/horizon/server.js` (the `submitTransaction` method's promise chain): its `.catch(function (response) { if (response instanceof Error) return Promise.reject(response); return Promise.reject(new BadResponseError(...)); })` guard is unconditionally true for a real Axios failure (an `AxiosError` IS an `Error`), so the `BadResponseError` branch is dead code in practice. This differs from `loadAccount`'s call-builder path (`_handleNetworkError` in `call_builder.js`), which DOES translate a 404 into a typed `NotFoundError` (see `docs/modules/api-wallet.md`'s `StellarAccountNotFoundError`). The practical consequence: `submit.ts` cannot use `instanceof NetworkError`/`BadResponseError` to detect `tx_bad_seq` — it duck-types the raw Axios error shape instead (`resultCodes`, `api/src/modules/sponsor/submit.ts:66-81`), reading `err.response.data.extras.result_codes.transaction`/`.operations` (`HorizonApi.ErrorResponseData.TransactionFailed` / `HorizonApi.TransactionFailedResultCodes`, verified against `.../lib/horizon/horizon_api.d.ts`; `TransactionFailedExtras.result_codes.operations: string[]` confirmed at the same file). `StellarGateway.submitTransaction` (`docs/modules/api-wallet.md`) deliberately does NOT translate this shape into a typed error the way `loadAccount` does — `submitAndClassify` (`submit.ts`) is the one place that inspects it.
- **`tx_failed`'s per-operation codes were dropped entirely before the `payments` module was added.** Before this change, only `result_codes.transaction` was extracted (as `transactionResultCode`, this function's earlier name) — for `tx_failed` (Horizon's generic "one of the operations failed" result), `SubmissionFailedError.reason` was just the bare string `'tx_failed'`, discarding Horizon's more specific `result_codes.operations` array entirely (e.g. `'op_no_trust'` for a payment to a destination with no trustline). Needed because the `payments` module's spec required a sanitized-but-specific reason to surface through `POST /intents/:id/complete`'s `submission_failed` response (`docs/modules/api-payments.md`'s Gotchas) — a bare `'tx_failed'` gives an API consumer no actionable information. `resultCodes` now extracts both fields, and `sanitizedReason` (`submit.ts:94-101`) appends the first non-`'op_success'` operation code specifically for `'tx_failed'`, e.g. `'tx_failed:op_no_trust'`. Every other transaction-level code (`'tx_insufficient_fee'`, `'tx_bad_auth'`, etc.) is already self-explanatory and is returned unchanged — only `'tx_failed'` needed this treatment.
- **`wrapFeeBump` is fully deterministic given the same inputs — verified directly, not assumed — which `intents/service.ts`'s pre-computed-txHash mechanism relies on (`docs/modules/api-intents.md`'s Gotchas).** `TransactionBuilder.buildFeeBumpTransaction` (which `wrapFeeBump` calls) has no randomness: its output is a pure function of `feeSource`/`baseFee`/the inner tx's own bytes (including the inner tx's already-attached signatures, since the inner tx's whole signed envelope is embedded in the fee-bump). A transaction's `hash()` is computed over its *signature base*, which excludes its own signatures — so the fee-bump's hash doesn't even depend on `wrapFeeBump`'s `fb.sign(sponsor)` call. Confirmed with a standalone script calling `wrapFeeBump` twice with identical inputs: byte-identical hash AND byte-identical signature both times (Stellar/ed25519 signing is itself deterministic per RFC 8032, though the hash doesn't depend on this). This determinism is now a documented CONTRACT on `IntentSubmitter.buildSubmission` itself (`intents/service.ts:44-56`), not just an observation about `wrapFeeBump` — `createPaymentSubmitter`'s `buildSubmission` IS `wrapFeeBump`, and `complete()` only ever hashes the ONE `built` instance `buildSubmission` returns (never rebuilds it before `submit`), so this determinism is what makes "hash it once, submit that exact object" correct.
- **`createSorobanSubmitter` fee-bumps at `SOROBAN_INVOKE_FEE` (`'1000000'`), never `wrapFeeBump`'s default `'10000'`.** Same reasoning as the `wrapFeeBump`-default-too-low bullet above, restated as this factory's own fixed choice rather than a caller-supplied argument: a Soroban invoke tx's own inclusion fee is far above a classic payment's, so a low `baseFee` would make `buildFeeBumpTransaction` throw `"Invalid baseFee..."`. Verified in `submit.test.ts` by asserting the resulting `FeeBumpTransaction.fee` equals `SOROBAN_INVOKE_FEE * (innerOps + 1)` for a single-operation inner tx (`'2000000'`).
- **`createSorobanSubmitter` has no `tx_bad_seq`/`StaleSequenceError` classification, unlike the two Horizon-backed factories.** `SorobanGateway.sendAndConfirm` throws `SorobanSubmissionError` with an already-short, already-sanitized `reason` (`'send_error'`/`'tx_failed'`/`'tx_not_found'`, `../../lib/soroban-gateway.ts:49-54`) — never Horizon's raw Axios error shape `resultCodes`/`sanitizedReason` decode — so `submitAndClassifySoroban` passes `err.reason` straight through into `SubmissionFailedError` with no stale-sequence special case. A genuinely stale merchant sequence number on a vault intent surfaces as a generic `submission_failed` 502 through `intents/service.ts`'s completion flow, not the more specific `intent_expired` 409 the Horizon-backed factories can produce.
- **`submitIntentTx` (the old single entry point, kind-branched inline) is DELETED — replaced by `createProvisionSubmitter`/`createPaymentSubmitter`, each a closure over its own fixed strategy instead of a runtime `kind` parameter.** Where `submitIntentTx({kind, sponsor, inner, gateway})` used to take `kind` as an explicit input and branch on it every call, the kind is now baked in at construction time: `app.ts` calls `createProvisionSubmitter(deps.stellarGateway)` and `createPaymentSubmitter(deps.sponsorKeypair, deps.stellarGateway)` ONCE at startup and registers the results into `IntentsServiceDeps.submitters` (`docs/modules/api-intents.md`), so `intents/service.ts`'s `complete()` never passes a `kind` string into this module at all — it just looks up `submitters[claimed.kind]` and calls that submitter's `buildSubmission`/`submit`. Both factories' `submit` delegate to the same module-private `submitAndClassify(gateway, built)` (`submit.ts:112-123`), so the Horizon-error classification logic itself is shared and unchanged, just no longer gated behind a `kind === 'provision' ? ... : ...` branch.

## Testing

- Unit tests in `api/src/modules/sponsor/stellar.test.ts` (4 tests):
  - `txHashHex` — verifies 0x-prefixed 64-char hex output.
  - `attachRawSignature` — attaches a valid signature and rejects signatures from wrong keys.
  - `wrapFeeBump` — wraps an inner tx with sponsor as fee source and signer, verifies sponsor signature on the fee-bump.
- Unit tests in `api/src/modules/sponsor/submit.test.ts` (13 tests, up from 9 — the `createSorobanSubmitter` addition contributed 4), split into three `describe` blocks:
  - `createProvisionSubmitter` (6 tests): `activityType` is `'provision'`; `buildSubmission` is identity — asserts `built === inner` and `built` is NOT a `FeeBumpTransaction`, then `submit(built, ...)` submits that exact instance directly (asserts the fake gateway received it unchanged); a `tx_bad_seq`-shaped fake Horizon rejection (see the Gotchas finding above for why the fake is shaped as a raw Axios error, not a stellar-sdk error class) throws `StaleSequenceError`; a different Horizon failure code throws `SubmissionFailedError` with that exact code as `reason`; **a `tx_failed`-shaped fake rejection with an empty `operations` array falls back to the bare `reason: 'tx_failed'`** (no informative op-level code to append); a plain non-Horizon-shaped `Error` (e.g. a network timeout) falls back to `reason: 'unknown_error'` rather than crashing on the duck-typing checks.
  - `createPaymentSubmitter` (3 tests): `activityType` is `'send'`; `buildSubmission` wraps in `wrapFeeBump(sponsor, inner)` — asserts the built tx IS a `FeeBumpTransaction` with `feeSource === sponsor.publicKey()`, then `submit` submits that exact fee-bump instance; **`op_no_trust`: a `tx_failed`-shaped fake rejection with `operations: ['op_success', 'op_no_trust']` produces `reason: 'tx_failed:op_no_trust'`** (also proves a leading `'op_success'` entry from an unrelated successful operation is skipped, not mistaken for the failure).
