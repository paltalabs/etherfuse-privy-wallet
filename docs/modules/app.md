## Purpose

Frontend workspace named `app` (`app/package.json:2`) — a Vite + React 19 SPA hosting the wallet UI (Privy embedded-wallet auth, Etherfuse ramp flows, DeFindex vault views). The app is gated behind `AuthGate` (login → Stellar wallet provisioning → authenticated context), then routed through a `react-router` route table rendered inside a shared `Layout`. `Dashboard`, `Send`, `Activity`, `OnRamp` (the 4-state Etherfuse onboarding ladder plus the `ready`-status pix payin flow), `OffRamp` (onboarding gate plus the `ready`-status Stellar payout flow), and `Earn` (vault position card plus deposit/withdraw forms, honest about the vault's current fail-closed backend state) are real, React-Query-backed screens; `Receive` is a real screen too (QR code + full address + copy-to-clipboard, reading `walletAddress` straight off `useCore()` — no network call); `KycReturn` is a real redirect-landing screen (not a nav destination) for Etherfuse's hosted `/idv` flow's `return_url`.

## Key methods

- `createApiClient(baseUrl, getToken, fetchFn?)` (`app/src/core/client.ts:26-58`) — returns an `ApiClient` (`{get, post}`). Each call: resolves `getToken()`; throws `ApiError(401, 'no_token')` **without calling `fetchFn`** if it resolves `null`; otherwise sends `Authorization: Bearer <token>` (+ `content-type: application/json` and a JSON body for POST); on non-2xx, tries to read a `{code}` field from the body and throws `ApiError(res.status, code ?? 'unknown_error')`; on a `204`, returns `schema.parse(undefined)` WITHOUT calling `res.json()` (`client.ts:54`) — a `204` has no body, and `res.json()` on one throws (empty string isn't valid JSON); this is what makes `z.void()` a legal response schema for `useSimulatePayin` below; on any other 2xx, parses the body through the caller-supplied zod `schema` (a failing parse propagates the zod error). `fetchFn` defaults to global `fetch`, injectable for tests.
- `ApiError` (`app/src/core/client.ts:4-14`) — `extends Error`, carries `status: number` and `code: string` as explicit fields assigned in the constructor body (not TS parameter-property shorthand — `app/tsconfig.app.json`'s `erasableSyntaxOnly: true` rejects that syntax, same pattern as `api/src/lib/errors.ts`'s `AppError`).
- `centsToDecimal(cents: number): string` (`app/src/core/format.ts:2-6`) — integer cents → 2dp decimal string (e.g. `123456` → `'1234.56'`).
- `formatAmount(amount: string): string` (`app/src/core/format.ts:9-13`) — Stellar 7dp decimal string → trimmed display form, trailing zeros stripped but never below 2dp (e.g. `'10.5000000'` → `'10.50'`, `'0.0000001'` → unchanged).
- `CoreProvider`/`useCore()` (`app/src/core/context.tsx:14-16,18-22`) — `useCore()` throws if called outside a `CoreProvider`. `CoreValue` is `{client: ApiClient, signer: RawHashSigner | null, walletAddress: string | null}` (`app/src/core/context.tsx:5-10`); `signer` is `null` until the Stellar wallet exists (`AuthGate` guarantees it's non-null by the time screens render).
- `signAndComplete(client, signer, walletAddress, intent)` (`app/src/core/signing.ts:14-26`) — the one place every intent-producing mutation converges: calls `signer.signRawHash({address: walletAddress, chainType: 'stellar', hash: intent.hashHex})` (the API's `hashHex` is already `0x`-prefixed — passed through verbatim, per `api/src/modules/sponsor/stellar.ts:5`'s `txHashHex`), then posts the returned (also `0x`-prefixed) `signature` verbatim to `POST /intents/${intent.intentId}/complete`, parsed through `CompleteIntentResponseSchema`. Both `useProvision` and `useSendPayment` call this instead of duplicating the sign-then-complete sequence.
- `useWallet()` (`app/src/core/hooks/wallet.ts:6-9`) — `useQuery({queryKey: ['wallet'], ...})` over `GET /wallet`; `WalletResponseSchema`-typed. The query key `['wallet']` is the invalidation target every intent-completing mutation below refetches through.
- `useProvision()` (`app/src/core/hooks/wallet.ts:12-23`) — mutation: `POST /wallet/provision`; if the response is the already-provisioned branch (`'provisioned' in res`), resolves `{alreadyProvisioned: true}` without signing anything; otherwise calls `signAndComplete` on the pending branch (throws if `signer`/`walletAddress` are unavailable — unreachable in practice since `AuthGate` only renders screens once both exist). `onSuccess` invalidates `['wallet']` unconditionally, so the Dashboard's next render re-fetches and flips branches on its own.
- `useSendPayment()` (`app/src/core/hooks/payments.ts:7-20`) — mutation taking a `PaymentRequest` (`{destination, amount, assetCode}`): `POST /payments` (`PaymentResponseSchema`), then `signAndComplete`. `onSuccess` invalidates both `['wallet']` (balance changed) and `['activity']` — now consumed by `useActivity` below, so a completed send immediately refetches the feed's first page.
- `useActivity()` (`app/src/core/hooks/activity.ts:27-40`) — `useInfiniteQuery({queryKey: ['activity'], initialPageParam: null, ...})` over `GET /activity` (`ActivityFeedResponseSchema`-typed); `refetchInterval: (query) => activityRefetchInterval(query.state.data)` — the exported pure helper (`activity.ts:16-19`) returns `5000` while any loaded page has a `status: 'pending'` item and `false` otherwise (incl. before data loads), mirroring `payinStateRefetchInterval`'s poll-only-while-it-can-change rule; each page fetch appends `?before=<encodeURIComponent(cursor)>` when the page param is non-null, otherwise hits the bare path. `getNextPageParam: (lastPage) => lastPage.nextBefore` — returning `null` (the API's "feed exhausted" signal, `docs/modules/api-history.md`) is treated by TanStack Query v5 as "no more pages" (`getNextPageParam(...) != null` in `node_modules/.pnpm/@tanstack+query-core@5.101.4/.../infiniteQueryBehavior.js:107-109`), so `hasNextPage` flips to `false` with no extra translation in this hook.
- `onboardingRefetchInterval(data)` (`app/src/core/hooks/ramp.ts:32-34`) — pure helper: `5000` while `data?.status === 'verifying'`, else `false`. Exported so the polling rule is unit-testable without fake timers; `useOnboardingStatus` passes it straight into `refetchInterval: (query) => onboardingRefetchInterval(query.state.data)`.
- `useOnboardingStatus()` (`app/src/core/hooks/ramp.ts:37-43`) — `useQuery({queryKey: ['ramp', 'onboarding'], ...})` over `GET /ramp/onboarding` (`RampOnboardingStatusSchema`-typed: `{status: 'not_started' | 'verifying' | 'incomplete' | 'ready'}` — the 4-state Etherfuse ladder). This exact query key is the invalidation target `useStartOnboarding`/`useCompleteSetup` below target.
- `useStartOnboarding()` (`app/src/core/hooks/ramp.ts:51-59`) — mutation taking an `OnboardingStartRequest` (`{displayName, email}`): `POST /ramp/onboarding/start` (`KycLaunchResponseSchema`-typed: `{launch: {actionUrl, assertion, target, returnUrl}}`). Creates the Etherfuse org and returns the hosted KYC launch parameters in the SAME call. `onSuccess` invalidates `['ramp', 'onboarding']` — a freshly-created `ramp_customers` row flips `not_started` to `verifying`.
- `useKycLaunch()` (`app/src/core/hooks/ramp.ts:67-73`) — mutation taking the SAME `OnboardingStartRequest` shape: `POST /ramp/onboarding/kyc-launch` (same `KycLaunchResponseSchema` response). Re-issues fresh launch parameters — used by `OnRamp`'s `verifying` state to relaunch after a denied/abandoned `/idv` run or a page reload. Doesn't itself change onboarding status, so no invalidation.
- `useCompleteSetup()` (`app/src/core/hooks/ramp.ts:80-87`) — mutation taking a `PixDetailsRequest` (`{firstName, lastName, cpf, pixKey, pixKeyType}`): `POST /ramp/onboarding` (`RampOnboardingStatusSchema`-typed response). `onSuccess` invalidates `['ramp', 'onboarding']` unconditionally, so `OnRamp`'s next render re-fetches and flips phases on its own — mirrors `useProvision`'s `['wallet']` invalidation above.
- `usePayinQuote()` (`app/src/core/hooks/ramp.ts:90-95`) — mutation taking a `PayinQuoteRequest` (`{amountBrlCents}`): `POST /ramp/payin/quote` (`RampQuoteResponseSchema`-typed: `{quoteId, expiresAt, senderAmountCents, receiverAmountCents, flatFeeCents, commercialQuotation}`). No invalidation — quoting has no server-side side effect.
- `useCreatePayin()` (`app/src/core/hooks/ramp.ts:105-111`) — mutation taking a `PayinExecuteRequest` (`{quoteId, amountCents}` — `amountCents` is the SAME quote's own `receiverAmountCents` echoed back, not re-derived, `docs/modules/api-ramp.md`'s Gotchas): `POST /ramp/payin` (`PayinOrderResponseSchema`-typed: `{orderId, status, deposit, receiverAmountCents}`). `onSuccess` invalidates `['activity']` (not `['ramp', 'onboarding']`) — the server writes a pending `on_ramp` activity row on success, mirroring `useSendPayment`'s `['activity']` invalidation.
- `payinStateRefetchInterval(data)` (`app/src/core/hooks/ramp.ts:121-123`) — pure helper, same shape as `onboardingRefetchInterval`: `5000` while `data?.status` is `'created'` or `'funded'` (the only statuses that can still change without user action), else `false`.
- `usePayinState(orderId)` (`app/src/core/hooks/ramp.ts:126-133`) — `useQuery({queryKey: ['ramp', 'payin', orderId], ...})` over `GET /ramp/payin/:orderId` (`PayinOrderStateResponseSchema`-typed: `{orderId, status, txHash}`), `refetchInterval` wired to `payinStateRefetchInterval`. Always enabled — only mounted (via `OnRamp.tsx`'s `DepositPanel`) once a concrete `orderId` exists.
- `useSimulatePayin(orderId)` (`app/src/core/hooks/ramp.ts:144-150`) — mutation with no input: `POST /ramp/payin/:orderId/simulate` with a `z.void()` response schema (see `createApiClient`'s 204 handling above) — the testnet-only sandbox deposit simulator, 404s outright on mainnet before any lookup. `onSuccess` invalidates `['ramp', 'payin', orderId]` so the UI reflects the simulated deposit without waiting for the next poll tick.
- `usePayoutQuote()` (`app/src/core/hooks/ramp.ts:154-159`) — mutation taking a `PayoutQuoteRequest` (`{amountCents}`, the sender-side settlement-token amount): `POST /ramp/payout/quote` (same `RampQuoteResponseSchema` shape `usePayinQuote` uses). No invalidation — quoting has no server-side side effect, mirroring `usePayinQuote`.
- `useCreatePayout()` (`app/src/core/hooks/ramp.ts:174-188`) — mutation taking a `PayoutExecuteRequest` (`{quoteId, amountCents}` — `amountCents` is the SAME quote's own `senderAmountCents` echoed back, same rationale as `useCreatePayin`): `POST /ramp/payout` (`PayoutIntentResponseSchema`-typed: `{intentId, xdr, hashHex}`), then `signAndComplete` (throws `'wallet signer unavailable'` if `signer`/`walletAddress` are unset — same defensive guard `useProvision` uses, unreachable in practice since `AuthGate` guarantees both). `onSuccess` invalidates BOTH `['wallet']` (the payout moves the settlement token out of the merchant's balance) AND `['activity']` (the server writes a pending `off_ramp` activity row on success) — the only hook in this ramp file invalidating two keys at once.
- `useVaultPosition()` (`app/src/core/hooks/vault.ts:12-18`) — `useQuery({queryKey: ['vault', 'position'], ...})` over `GET /vault/position` (`VaultPositionResponseSchema`-typed: `{shares, underlyingBalance, assetCode, assetIssuer}`). Zeros for a merchant with no position (`docs/modules/api-vault.md`'s endpoint table) — this hook has no special-casing for that, it's just another successful response shape.
- `invalidateVaultQueries(qc)` (`app/src/core/hooks/vault.ts:21-25`, module-private) — invalidates `['vault', 'position']`, `['wallet']`, and `['activity']`; shared by both mutations below since a deposit/withdraw always changes all three (the vault position, the merchant's USDC balance, and the activity feed's pending row).
- `useVaultDeposit()` (`app/src/core/hooks/vault.ts:41-52`) — mutation taking a `VaultDepositRequest` (`{amount}`): `POST /vault/deposit` (`VaultIntentResponseSchema`-typed: `{intentId, xdr, hashHex}`), then `signAndComplete` — same sign-then-complete convergence `useCreatePayout` uses (throws `'wallet signer unavailable'` if `signer`/`walletAddress` are unset, same unreachable-in-practice guard). **Whether this currently fails closed is not yet re-verified.** `TESTNET_VAULT` now pins a real deployed DeFindex vault (`docs/modules/api-vault.md`), so `/vault/*` registers on testnet and `client.post('/vault/deposit', ...)` no longer 404s outright — but whether a live deposit succeeds, or still fails closed with `ApiError(502, 'simulation_failed')`, has not been confirmed live. `vault.test.tsx`'s dedicated 502 test (asserting `signRawHash` is never called on that specific rejection) is still valid coverage of the module's OWN error-propagation logic against a fake client, regardless of what a live call currently returns.
- `useVaultWithdraw()` (`app/src/core/hooks/vault.ts:55-66`) — same shape as `useVaultDeposit`, taking a `VaultWithdrawRequest` (`{shares}`) against `POST /vault/withdraw`; same fail-closed 502 behavior.
- `EarningCard()` (`app/src/screens/Dashboard.tsx:36-45`) — reads `useVaultPosition()`; renders `formatAmount(position.data.underlyingBalance)` plus `position.data.assetCode` once `isSuccess`, otherwise `—` for BOTH the loading and error states. This containment is deliberate: a vault-position read failure (e.g. the same 502 outage `useVaultDeposit`/`useVaultWithdraw` hit) must never break the rest of `BalanceCard`/`Dashboard` — `Dashboard.test.tsx` proves the balance card and Send link still render when `/vault/position` rejects.
- `PositionCard()` (`app/src/screens/Earn.tsx:51-76`) — the Earn screen's own vault-position display: `Loading…` while `position.isLoading`, the raw `ApiError` code in a `.error` box on failure (unlike `Dashboard`'s silent `—`, since this IS the Earn screen — a visible code is more useful here than a blank dash), otherwise the underlying-balance headline (`formatAmount`) + asset code, plus a `formatAmount(position.data.shares)` shares line below.
- `isVaultUnavailable(error)` (`app/src/screens/Earn.tsx:18-20`) — `true` iff `error instanceof ApiError && error.status === 502 && error.code === 'simulation_failed'`, the exact shape `docs/modules/api-vault.md`'s Gotchas documents for the vault's fixed, sanitized simulation-failure token.
- `MutationFeedback({error})` (`app/src/screens/Earn.tsx:26-31`) — renders the persistent, non-`.error` `.info` banner (exact copy: *"Earning deposits are temporarily unavailable — the vault can't accept this asset until its balance is authorized by the asset's issuer. Your funds have not moved."*, `VAULT_UNAVAILABLE_MESSAGE`, `Earn.tsx:22-23`) when `isVaultUnavailable(error)`; otherwise falls back to the plain `.error` `errorCode(error)` box every other screen uses. Shared by both `DepositForm` and `WithdrawForm`'s error slots — the message is intentionally worded around "deposits" even for a withdraw failure since both mutations fail for the exact same underlying reason (the vault contract's own balance, not the merchant's), per the task's exact degradation-contract copy.
- `DepositForm()`/`WithdrawForm()` (`app/src/screens/Earn.tsx:78-112`/`114-150`) — controlled `amount`/`shares` inputs; submit runs `VaultDepositRequestSchema.safeParse({amount})`/`VaultWithdrawRequestSchema.safeParse({shares})` client-side first (shows the first zod issue's message on failure, network never reached — same pattern as `Send.tsx`/`OnRamp.tsx`/`OffRamp.tsx`), then `.mutate(parsed.data)`. `isSuccess` renders a shared `SuccessPanel` (`Earn.tsx:33-48`, mirroring `Send.tsx`'s/`OffRamp.tsx`'s `txHash` + `explorerTxUrl` pattern) with a reset button ("Deposit more"/"Withdraw more") calling `.reset()`. `isError` renders `MutationFeedback`. ## Gotchas & invariants

- **`app/tsconfig.app.json`'s `erasableSyntaxOnly: true` rejects TypeScript constructor parameter-property shorthand** (`constructor(readonly x: number)`) — `tsc -b` fails with `TS1294`. `ApiError` (`app/src/core/client.ts:4-14`) uses explicit field declarations + constructor-body assignment instead, matching `api/src/lib/errors.ts`'s `AppError` pattern. Watch for this if copying class snippets that use parameter properties.
- **`app` has no `typecheck` script — only `build` runs `tsc -b && vite build`** is no longer true: `typecheck` (`tsc -b --noEmit`) now exists (`app/package.json:12`) alongside `test` (`vitest run`, `app/package.json:11`).
- Lint uses `oxlint`, not eslint (`app/package.json:9`, `app/.oxlintrc.json`). `oxlint`'s `react/only-export-components` rule (set to `warn`, `app/.oxlintrc.json:6`) warns on `core/context.tsx` for exporting both a component (`CoreProvider`) and non-component values (`useCore`, the `CoreValue` type) from the same file — this is a warning, not a lint failure, and is the same file shape `useCore`'s single-context-file convention calls for.
- Env vars live in the **root** `.env`, not `app/.env.local` — `vite.config.ts` sets `envDir` to the repo root (`app/vite.config.ts:9`). Adding an `app/.env.local` would silently be ignored for `VITE_*` resolution.
- **`getAccessToken` (from `usePrivy()`) is not assumed to be referentially stable across renders.** `AuthGate.tsx:56-59` routes every call through a ref and memoizes the API client with an empty dependency array specifically so a changing `getAccessToken` identity can never cause the memoized client (and anything holding onto it, e.g. React Query) to be silently rebuilt every render.
- **The Stellar-wallet auto-provisioning call lives in a `useEffect`, not directly in the render body** (`AuthGate.tsx:47-51`, calling the shared `provisionWallet` at `AuthGate.tsx:36-43`) — calling an async side-effecting function unconditionally during render is unsafe under React 19's `StrictMode`/concurrent rendering (a render pass can be thrown away without committing, which would desync a render-phase ref flip from whether the call actually happened). The `creatingRef` guard additionally protects against `StrictMode`'s dev-mode double-invoke of effects.

Only the `email` field is ever prefilled, from `usePrivy()`'s `user?.email?.address`, since Privy's login flow already guarantees that value is a real, user-confirmed address.

Fixed via a `useState` initializer so the render-gating decision is captured once from `prefill` and never recomputed (`OnRamp.tsx:126-133`); the submit button's `disabled` check still reads the live `displayName` state (`OnRamp.tsx:173-177`), so typing still enables it — only the fields' mount/unmount is frozen.
