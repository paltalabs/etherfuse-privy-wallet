## Purpose

The `intents` module is the generic signing-flow completion surface: it takes a `pending` intent (built by another module — `wallet`'s `POST /wallet/provision` for `'provision'`-kind intents, `payments`'s `POST /payments` for `'payment'`-kind intents, `vault`'s `POST /vault/deposit`/`POST /vault/withdraw` for `'vault_deposit'`/`'vault_withdraw'`-kind intents, `ramp`'s `POST /ramp/payout` for `'payout'`-kind intents, `docs/modules/api-payments.md`/`docs/modules/api-vault.md`/`docs/modules/api-ramp.md`) plus the merchant's raw Privy signature, attaches the signature to the stored transaction, atomically claims the intent for submission (see Gotchas), submits it via that kind's registered `IntentSubmitter` (build the submission tx, then submit it — fee-bumped or direct, through Horizon, Soroban RPC, or a fiat off-ramp provider, decided entirely by which submitter is registered for the intent's `kind`, not by a branch in `complete()` itself), and updates the intent/merchant/activity records from the result — on success AND on failure. It is a sibling of `wallet`, `payments`, `vault`, and `ramp`, not a dependency of any of them — every producer module queries the shared `merchants`/`intents` (and, for `payments`/`vault`/`ramp`, `activity`) tables directly rather than importing one another's repo. `intents.kind` is widened to `'provision' | 'payment' | 'payout' | 'vault_deposit' | 'vault_withdraw'` (`db/schema.ts`) — every one of these five kinds now has a registered submitter (wired in `app.ts`). A claimed intent of an unregistered kind (should this union ever widen again without a corresponding `app.ts` entry) is an integrity bug, not a client-facing error (see Gotchas).

|---|---|---|---|---|

### Error responses

| Condition | Status | Body | Intent side-effect |
|---|---|---|---|
| `:id` is not a UUID | 404 | `{code: 'intent_not_found'}` | none — byte-identical to the "doesn't exist" row below, deliberately (see Gotchas) |
| Body fails `CompleteIntentRequestSchema` (missing/non-string `signature`) | 400 | `{code: 'invalid_request', details: {issues}}` | none |
| Intent doesn't exist, or belongs to a different `privyDid` | 404 | `{code: 'intent_not_found'}` | none |
| Intent status is `'submitted'` or `'submitting'` (already submitted, or a concurrent completion currently owns the atomic claim — see Gotchas) | 409 | `{code: 'intent_already_submitted', details: {resultTxHash}}` | none — never resubmits |
| Intent status is `'failed'` | 409 | `{code: 'intent_failed', details: {reason}}` | none — never resubmits |
| `attachRawSignature` throws (invalid/wrong-key signature) | 400 | `{code: 'invalid_signature'}` | **none — intent stays `'pending'`**, client can retry with a correct signature |
| Submission rejected with Horizon `tx_bad_seq` | 409 | `{code: 'intent_expired'}` | intent → `'failed'`, `error: 'stale_sequence'`; activity row written (`status: 'failed'`, `txHash: null`) |
| Any other submission failure | 502 | `{code: 'submission_failed', details: {reason}}` | intent → `'failed'`, `error: reason` (compact code, never raw Horizon `extras`); activity row written (`status: 'failed'`, `txHash: null`) |
| Submission succeeds | 200 | `{txHash}` | intent → `'submitted'`, `resultTxHash` set; activity row written (`status: 'confirmed'`, real `txHash`); `provision` intents also set `merchants.provisionedAt` |

## Gotchas & invariants

- **`getOwnedIntent`'s ownership check is baked into the query itself** (`and(eq(intents.id, id), eq(intents.privyDid, privyDid))`, `service.ts:135-141`) — a wrong-owner intent and a nonexistent one both resolve to `undefined`, producing the SAME 404. This is deliberate: a 403 would leak that the intent ID exists at all. `getOwnedIntent` is a plain read with no side effect — it is NOT the claim mechanism (see the atomic-claim bullet below).
- **`IntentsRepo` queries `merchants`/`intents`/`activity` directly, independent of `wallet/service.ts`'s `WalletRepo` and `payments/service.ts`'s `PaymentsRepo`** — none of the three modules share a repo or import from each other, even though `wallet`/`intents` touch the same two tables and `payments`/`intents` both touch `activity`. Keeps them decoupled siblings (`intents` is its own module because it serves both provisioning AND payment intents, which have nothing to do with each other beyond sharing this completion endpoint).
- **Failure-status handling uses two distinct codes, not one generic "already handled" code**: `intent_already_submitted` for a `'submitted'` OR `'submitting'` retry (both mean "someone already has this intent moving"), `intent_failed` for a `'failed'` retry. Both are 409 and both refuse to resubmit, but the codes tell the client which situation it's in (a `'failed'` intent needs a brand-new intent from `/wallet/provision`; a `'submitted'`/`'submitting'` one is already in flight or done). `nonPendingStatusError` (`service.ts:216-229`) is the single place this mapping lives, shared by both the fast-path check and the post-claim-failure fallback below, so the two call sites can never drift.
- **Atomic claim (`IntentsRepo.claimIntent`) is the real defense against two concurrent `complete` calls for the SAME intent double-submitting — the earlier fast-path status check alone was a TOCTOU bug.** Before that fix, `complete` read the intent once (`getOwnedIntent`), checked `status === 'pending'`, then went on to parse/verify/submit — nothing stopped two concurrent requests (e.g. a client retry racing the original, or two tabs) from both passing that read-then-check and both reaching the submitter, double-submitting (and double-writing activity rows/`provisionedAt`). The fix: immediately before looking up the submitter, `complete` calls `repo.claimIntent(id, privyDid)` — a single atomic `UPDATE intents SET status = 'submitting', updated_at = now() WHERE id = $id AND privy_did = $privyDid AND status = 'pending' RETURNING *` (`service.ts:142-149`). Postgres's row-level locking on that one `UPDATE` guarantees only ONE concurrent caller's statement matches `status = 'pending'` and gets a row back; every other caller's `claimIntent` resolves to `undefined` and must re-fetch to find out why (`service.ts:300-308`) — it never reaches a submitter or writes an activity row. **Placement matters**: the claim happens AFTER signature verification, not before — claiming first would leave an intent that fails signature verification stuck in `'submitting'` forever (the claim only ever moves `'pending' -> 'submitting'`, there is no path back to `'pending'`), breaking the "invalid signature leaves the intent retriable" contract. Signature verification has no side effects and never touches a submitter, so there is nothing to protect by claiming before it.
- **`complete()` routes to a submission strategy by kind via `deps.submitters[claimed.kind]` (`IntentSubmitter`, `service.ts:57-63`) instead of branching on `kind` inline — a missing entry is an integrity bug, not a client-facing error (submitter-routing widening, `service.ts:310-319`).** `intents.kind` widened to `'provision' | 'payment' | 'payout' | 'vault_deposit' | 'vault_withdraw'` (`db/schema.ts`) — `app.ts` now wires all five: `provision`/`payment`/`vault_deposit`/`vault_withdraw` (`createProvisionSubmitter`/`createPaymentSubmitter`/`createSorobanSubmitter`, `docs/modules/api-sponsor.md`) and `payout` (`createPayoutSubmitter`, `docs/modules/api-ramp.md`). `IntentsServiceDeps.submitters` stays typed `Partial<Record<IntentKind, IntentSubmitter>>` — it was introduced so the map could start without every kind, and remains `Partial` since nothing in the type system enforces every kind stays registered as `IntentKind` widens further; if `complete()` ever claims an intent whose `kind` has no registered submitter (a drift between an intent producer and `app.ts`'s wiring — currently unreachable, since `wallet`/`payments`/`vault`/`ramp` produce intents today and all five of their kinds have submitters), it throws a plain `Error` (→ generic 500), the same integrity-error treatment as the "merchant does not exist" check below — never an `AppError`, since this is a deployment bug the client can't fix by retrying. `gateway`/`sponsor`/`rampProvider` never appear in `IntentsServiceDeps` at all — they're captured inside each submitter's closure instead (`createProvisionSubmitter(gateway)`/`createPaymentSubmitter(sponsor, gateway)`/`createSorobanSubmitter(sponsor, sorobanGateway, activityType)`/`createPayoutSubmitter(sponsor, gateway)`) — note `createPayoutSubmitter` takes a `StellarGateway`, the SAME kind of dependency `createPaymentSubmitter` closes over, NOT a `RampProvider` (see the header note above for why).
- **`complete` pre-computes the submission tx's hash and writes it onto the pending activity row BEFORE calling `submit()` — closes a crash-window gap in the indexer's dedupe (`IntentsRepo.updateActivityTxHash`, `service.ts:111-128`/`177-182`, called at `service.ts:358-359`).** Immediately after the atomic claim succeeds and a submitter is resolved, `complete` calls `submitter.buildSubmission(tx)` — the plain `tx` for `'provision'` (identity), `wrapFeeBump(sponsor, tx)` for `'payment'` — hashes the RESULT with `txHashHex` (stripping the `0x` prefix so the stored value matches Horizon's own hash format, the same format `result.txHash`/`HorizonPaymentRecord.transactionHash` use), and calls `repo.updateActivityTxHash(activityExternalRef ?? claimed.id, merchant.stellarAddress, precomputedTxHash)` — all before `submitter.submit(built, {intent: claimed, merchant})` is ever called, and `submit` receives that exact `built` instance (never rebuilt internally). **The `activityExternalRef ?? claimed.id` key here is NOT a leftover from the `activityExternalRef` contract bullet below — it is REQUIRED for this specific write to do its job for a reconciler-keyed row.** An earlier revision of this fix hardcoded this call to `claimed.id` even after adding `activityExternalRef` elsewhere in `complete()` — for a `'payout'` intent (the one kind that sets it), `claimed.id` never matches that row's real `externalRef`, so the write silently found nothing to update; a crash between Horizon accepting the submission and the (separate) post-submit write below would then leave the row `txHash: null` forever, and `indexer/poller.ts`'s cross-type dedupe (keyed on `txHash`, `poller.ts:218-227`) could never match it, inserting a duplicate `'send'` row instead of confirming this one. Caught and fixed same-day (see this file's own header and Testing section). Before the ORIGINAL fix (which introduced this pre-computed write at all), a process crash between submission succeeding and `markSubmitted`/`recordActivity` running left a payment's pending `activity` row stuck at `txHash: null` forever, which the indexer's dedupe-by-`(txHash, stellarAddress, type)` could never match (see `docs/modules/api-indexer.md`'s Gotchas) — producing a permanent duplicate row once the indexer saw the payment confirm on-chain. With the hash written up front (and, now, keyed correctly for every kind), that same crash leaves a row the indexer CAN match and flip to `'confirmed'`. **Determinism is load-bearing and is now a documented CONTRACT on `IntentSubmitter.buildSubmission`** (`service.ts:44-56`), not just an implementation detail of one submitter: `wrapFeeBump`'s `TransactionBuilder.buildFeeBumpTransaction` call has no randomness (feeSource/baseFee/already-signed inner tx fully determine the output), and a transaction's `hash()` is computed over its signature base, which excludes its OWN signatures — so the hash `complete()` precomputes from `buildSubmission`'s return value is guaranteed to equal the hash of whatever `submit()` actually submits, since it's literally the same object, not a second independently-built one; confirmed with a standalone script building the same fee-bump twice and comparing hash+signature bytes (`docs/modules/api-sponsor.md`'s Gotchas). A no-op for `'provision'`-kind intents (no pending row ever exists for them, see below) and safe to call unconditionally on every completion.
- **`recordActivity` is upsert-by-`externalRef`, not a plain insert — added for the `payments` module (`docs/modules/api-payments.md`), a second intent producer that DOES write a pending `activity` row at creation time (unlike `wallet/service.ts`'s `provision()`, which writes none).** Before this change, `recordActivity` always `INSERT`ed; a completed payment would then leave a permanent pending+confirmed (or pending+failed) double row for the same payment with no reconciliation path. The fix (`createDrizzleIntentsRepo.recordActivity`, `service.ts:168-175`): look up an existing `activity` row by `eq(activity.externalRef, input.externalRef)`; if one exists, `UPDATE` only its `status`/`txHash` in place (leaving creation-time fields like `counterparty`/`amount`/`assetCode`/`assetIssuer` — which `ActivityInput` doesn't even carry — untouched); otherwise `INSERT` as before. `complete` (`service.ts`) passes `externalRef: activityExternalRef ?? claimed.id` on its two FAILURE-path `recordActivity` calls (the `tx_bad_seq` branch and the other-failure branch) — see the `activityExternalRef` bullet below for what that resolves to and why; its SUCCESS-path write is conditional on the same value (see that bullet). For every kind without `metadata.activityExternalRef` (the default), this resolves to `claimed.id`, exactly the pre-fix behavior: a `'payment'` intent's pending row (written by `payments/service.ts` with `externalRef` = the intent's own id) gets updated in place; a `'provision'` intent has no pre-existing row to match, so `recordActivity` falls through to its original insert behavior, unchanged. `ActivityInput` itself carries a required `externalRef: string` field to carry this (`service.ts:35-42`) — `ActivityInput.type` is `IntentActivityType`, taken from `submitter.activityType`, not derived from `claimed.kind` inline anymore (see the submitter-routing bullet above).
- **`activityExternalRef` (`intents.metadata.activityExternalRef`, optional) is a GENERIC, KIND-AGNOSTIC contract: when an intent's metadata carries it, that intent's pending `activity` row was tagged with a DIFFERENT `externalRef` than the intent's own id — so `complete()` writes that row's `txHash` on success/failure but deliberately does NOT touch its `status` itself.** Computed once (`const activityExternalRef = claimed.metadata?.activityExternalRef;`, `service.ts:358`) and threaded through EVERY write that follows it in `complete()`, INCLUDING the pre-submission crash-window write immediately below it (`service.ts:359` — this is load-bearing, see the crash-window bullet above; getting this one wrong was a same-day F1 bug this fix wave corrected): on SUCCESS, if set, `complete()` calls `repo.updateActivityTxHash(activityExternalRef, merchant.stellarAddress, result.txHash)` and does **NOT** call `recordActivity` (`service.ts:407`) — it never writes `status` for this row; if unset, behavior is exactly the pre-existing `recordActivity({status: 'confirmed', ...})` call keyed by `claimed.id`. On FAILURE (both the `tx_bad_seq` and generic-failure branches), the `recordActivity` call's `externalRef` becomes `activityExternalRef ?? claimed.id` (`service.ts:373`/`385`) — when set, this MATCHES the existing pending row (upsert-by-`externalRef`, see the bullet above) and flips it straight to `'failed'`, rather than inserting an unrelated second row keyed by the intent's own id. **Why success doesn't confirm the row: `indexer/poller.ts`'s Horizon-payments poller already does, independently, the moment it next sees the matching on-chain payment** — `RAMP_OWNER_TYPE`'s cross-type dedupe check (`poller.ts:218-227`) matches a normalized `'send'` record against a pending `'off_ramp'` sibling by `(txHash, stellarAddress)` and confirms it there, the SAME mechanism that confirms every other pending row this codebase writes. `complete()` NOT also confirming it here isn't "leaving it for a reconciler to eventually pick up" — it's "not duplicating a confirmation the indexer already owns". This is exactly WHY getting the pre-submission write's key right (the crash-window bullet above) matters so much for a reconciler-keyed row: if that write silently fails to land the real `txHash`, the indexer's `txHash`-keyed dedupe can never find the row either, and NOTHING confirms it. **Why this field exists**: `ramp/service.ts`'s `createPayout` is the only current setter — it tags its pending `off_ramp` row `externalRef: 'order:<orderId>'` (the LOCALLY-generated `orderId`, not Etherfuse's echoed one), a DIFFERENT key than `claimed.id`, so a FUTURE order-status reconciler (not built yet) can find it purely from the Etherfuse order id for the one thing the Horizon indexer genuinely can't see: the FIAT-side exception path where Etherfuse's fiat leg fails/refunds/cancels independently of the on-chain payment (`docs/modules/api-ramp.md`'s payout Gotchas). Before the `activityExternalRef` fix existed at all, `complete()`'s hardcoded `externalRef: claimed.id` on every activity write could never match that row, so a completed (or failed) payout silently left the pending row untouched FOREVER and inserted a second, orphaned `off_ramp` row instead — a real defect, caught and fixed same-day.
- **`'submitting'` is a new `intents.status` value with no Postgres-level enforcement.** `intents.status` is plain `text` with a TypeScript-only `$type<'pending' | 'submitting' | 'submitted' | 'failed'>()` (`db/schema.ts:43`) — there is no `pgEnum` or `CHECK` constraint, so this value is enforced entirely by application code (`intents/service.ts`, this doc). Same is true of the widened `kind` union — plain `text`, no DB constraint, so widening it to add `payout`/`vault_deposit`/`vault_withdraw` was a type-only change with no migration (`docs/modules/api.md`-level convention; only `intents.metadata`, a genuinely new column, needed one — see below).
- **`intents.metadata` (`jsonb`, nullable, `db/schema.ts:46-75`) is a new column added for the same widening — kind-specific side-channel data an `IntentSubmitter`'s PRODUCER (or, for `activityExternalRef`, `complete()` itself) needs beyond the stored XDR itself**, typed `{quoteId?: string; orderId?: string; activityExternalRef?: string}`. `quoteId` is reserved for a future ramp-provider integration that needs to re-reference a quote at authorize time and is unused by anything today; `orderId` is what `ramp/service.ts`'s `createPayout` stamps (`metadata: {orderId: details.orderId, activityExternalRef}`, `ramp/service.ts:703-710`) — the Etherfuse anchor order's own id, recorded for a FUTURE reconciliation pass, not consumed by `createPayoutSubmitter` itself (which needs no provider round-trip and therefore no side-channel data at all — see `docs/modules/api-ramp.md`'s Gotchas); `activityExternalRef` is the GENERIC contract described in its own bullet above. Unused by `createProvisionSubmitter`/`createPaymentSubmitter` (both ignore it) — the ONE column in this migration wave that isn't just a `$type` union widening, since `jsonb` needed an actual `ALTER TABLE ... ADD COLUMN` (`api/drizzle/0001_kind_kingpin.sql`) — both `orderId`'s and `activityExternalRef`'s own additions to the TS `$type` were type-only follow-ups needing no further migration (still `jsonb`).
- **Known debt: an intent stuck in `'submitting'` after a process crash currently needs manual DB repair.** If the process crashes (or the pod is killed) between `claimIntent` succeeding and `markSubmitted`/`markFailed` running, the intent is left in `'submitting'` forever — `claimIntent`'s `WHERE status = 'pending'` will never match it again, so `complete` will keep responding 409 `intent_already_submitted` for that intent, and the client has no way to force a retry (unlike a `'failed'` intent, there's no user-facing path back to `'pending'`). No recovery machinery (a timeout-based re-claim, a reconciliation job, etc.) is built for this yet — deliberately out of scope, since this crash window is a rare edge case for an MVP. A future indexer/reconciliation effort should either detect and manually fix stuck `'submitting'` rows, or add a stale-claim timeout to `claimIntent`'s `WHERE` clause (e.g. also match rows in `'submitting'` for longer than N minutes). (This is a DIFFERENT crash window from the pre-computed-txHash fix above — this one is about `intents.status` getting stuck, that one is about `activity.txHash` staying null; the two happen at different points in `complete` and neither one closes the other.)
- **`complete` never mutates the DB before signature verification succeeds.** `attachRawSignature`'s throw is caught and re-thrown as `AppError('invalid_signature', ..., 400)` with zero repo calls in between (including no claim attempt — see the atomic-claim bullet above) — the intent is byte-for-byte unchanged in `'pending'` status, so the client can simply retry the same request with a corrected signature.
- **Stored intent XDR is always a plain `Transaction`, never a `FeeBumpTransaction`.** `TransactionBuilder.fromXDR`'s return type is a union only because arbitrary XDR could be either; this module asserts `parsed instanceof Transaction` and throws an internal (non-`AppError`, 500-surfacing) error if that invariant is ever violated — see `service.ts:272-274`. This holds today because both intent producers (`wallet/service.ts`'s `provision()` and `payments/service.ts`'s `createPayment()`) always store `tx.toXDR()` from a `TransactionBuilder`-built `Transaction`. This is also why `IntentSubmitter.buildSubmission(inner: Transaction)` takes a plain `Transaction`, never a `FeeBumpTransaction`, as its input.
- **A missing `merchants` row for an owned intent is treated as a programmer/integrity error, not a client-facing 404.** `intents.privyDid` has a `NOT NULL` foreign key into `merchants.privyDid` (`db/schema.ts:33-35`), so this should be unreachable; `service.ts:259-265` throws a plain `Error` (→ generic 500) rather than inventing a client-facing code for a state that should never occur — the same treatment as the missing-submitter integrity error above.
- **No DB transaction wraps the multi-step success path** (`markSubmitted` → `recordActivity` → optionally `markMerchantProvisioned`) — same lack of transactionality as `wallet/service.ts`'s `provision()`, which also does sequential un-transacted writes. Not a gap introduced by this module specifically; a partial failure between these calls (e.g. process crash) would need reconciliation by a future indexer, same as the existing wallet-module gap already documented in `docs/modules/api-wallet.md`. (This is distinct from both crash windows described above, which happen earlier — before or during submission, not after it succeeds.)
- **Both failure branches (`tx_bad_seq` and any other submission failure) write an activity row via `recordActivity`** — `status: 'failed'`, `type` taken from `submitter.activityType`, `txHash: null` (this is unconditional regardless of `activityExternalRef`, unlike the success path — see that bullet above, which skips `recordActivity` entirely for a reconciler-owned row; a FAILED submission is always this module's own concern to report, never the external reconciler's) (nothing confirmed on-chain to point at, even though a pending row may briefly have carried the pre-computed hash — see the pre-computed-txHash bullet above; a genuinely rejected submission never lands on-chain under that hash, so nulling it here is correct). The activity feed is a full-lifecycle tracker of intent outcomes, not just a confirmed-events feed — an earlier version of this module wrote a row only on success, reasoning that `intents.status`/`error` already captured the failure state; that was an incorrect reading of the activity table's intended scope and has been corrected. `ActivityInput.status` is `'confirmed' | 'failed'` and `txHash` is `string | null` to allow this, and `externalRef: string` is required too — see the upsert-by-`externalRef` bullet above (`service.ts:35-42`).
- **Route param `:id` and the request body are both zod-validated in `routes.ts` before hitting the service.** `:id` goes through `IntentIdParamSchema` (`z.string().uuid()`) — a malformed id now throws the exact same `AppError('intent_not_found', 'intent not found', 404)` `service.ts`'s `getOwnedIntent` produces for a real miss, so a caller can never distinguish "not shaped like an id" from "no such intent" (previously, a malformed id reached Postgres directly and surfaced as an untyped `500`, not a `404`). The body goes through `CompleteIntentRequestSchema.safeParse` (not `.parse()`) — a missing/malformed `signature` now throws `AppError('invalid_request', ..., 400, {issues})` instead of an uncaught `ZodError` that `app.ts`'s error handler would map to a generic `500` (this was the one pre-existing gap `docs/modules/api-payments.md`'s Gotchas called out as "left as-is, out of scope" when `payments` added its own `safeParse` — now closed here too).
