## Purpose

The `vault` module talks to the DeFindex vault contract on Stellar testnet: it builds unsigned, simulated-and-assembled deposit/withdraw transactions sourced by the merchant, and reads a merchant's vault position (share balance + underlying-asset value). It follows the same "provider builds a tx, caller signs/submits" split as `sponsor`/`intents` — this module never signs or submits anything itself. `service.ts`/`routes.ts` sit on top of the provider layer and follow `payments/service.ts`'s exact shape: an HTTP surface producing pending, unsigned `vault_deposit`/`vault_withdraw` intents plus pending activity rows, submitted through the generic `POST /intents/:id/complete` endpoint (`docs/modules/api-intents.md`). Submission itself is a third `IntentSubmitter` strategy, `createSorobanSubmitter` (`api/src/modules/sponsor/submit.ts`) — the sponsor module owns generic submission strategies, so it lives there rather than in this module, same as `createProvisionSubmitter`/`createPaymentSubmitter`.

## Endpoints / Public surface

**Registered only when `deps.network.vault` is non-null** (`app.ts:178`, `if (vaultService) await authenticated.register(vaultRoutes, ...)`) — otherwise inside `app.ts`'s authenticated scope, requiring `Authorization: Bearer <Privy access token>` (see `docs/modules/api-auth.md`) and reading `request.privyDid`. **Currently registered on testnet**: `TESTNET_VAULT` pins the deployed HodlUSDC DeFindex vault (`api/src/config/vaults.ts:18-22`), so every path below is live there. `MAINNET_VAULT` is `null`, so on mainnet these routes are not registered and 404 (Fastify's own route-not-found response, not this module's `AppError` envelope).

| Method | Path | Body | Response | Notes |
|---|---|---|---|---|
| `GET` | `/vault/position` | — | `200 {shares, underlyingBalance, assetCode, assetIssuer}` | Zeros for an unprovisioned/zero-balance merchant (`defindex.ts`'s `ZERO_VAULT_POSITION` short-circuit — see `docs/modules/api-vault.md`'s prior Gotchas, still true). |
| `POST` | `/vault/deposit` | `{amount: string}` (7dp positive decimal) | `200 {intentId, xdr, hashHex}` | A pending, unsigned `vault_deposit` intent — submit via `POST /intents/:id/complete`. |
| `POST` | `/vault/withdraw` | `{shares: string}` (7dp positive decimal) | `200 {intentId, xdr, hashHex}` | A pending, unsigned `vault_withdraw` intent — same submission path. |

### Error responses

| Condition | Status | Body | Notes |
|---|---|---|---|
| Body fails `VaultDepositRequestSchema`/`VaultWithdrawRequestSchema` (bad amount/shares shape, e.g. `'0'` or more than 7 decimal places) | 400 | `{code: 'invalid_request', details: {issues}}` | `routes.ts`'s `safeParse`, never reaches the service. |
| Caller has never provisioned (`repo.getMerchant` returns nothing) | 404 | `{code: 'merchant_not_found', message: 'call POST /wallet/provision first'}` | Same envelope as `payments/service.ts`'s equivalent check. |
| `VaultProvider` throws `SorobanSimulationError` (deposit/withdraw tx build, or `position`'s internal `simulateRead`) | 502 | `{code: 'simulation_failed', message: 'transaction simulation failed', details: {detail: 'vault_simulation_failed'}}` | `details.detail` is a FIXED sanitized token, never `SorobanSimulationError.detail` (the provider's raw RPC diagnostic) — see Gotchas. |

## Gotchas & invariants

- **`invest: false` on `buildDepositTx` is load-bearing, not a default.** `TESTNET_VAULT` has no strategies attached (`api/src/config/vaults.ts:14-17`), so deposits are held as idle funds — passing `invest: true` would attempt to route into a strategy that does not exist and fail.
- **`buildWithdrawTx`'s `min_amounts_out: [0]` has no slippage protection**, acceptable only because the vault is idle-funds-only (no strategy P&L to slip against between simulation and submission).
- **`withdraw`'s pending activity row's `amount` is `null`, unlike every other pending-activity producer in this codebase (`payments/service.ts`'s `PendingPaymentActivity.amount` is always a known string).** The underlying-asset amount a merchant actually receives from a withdrawal isn't known until the on-chain call executes — the share→asset conversion rate (`get_asset_amounts_per_shares`, `defindex.ts:109-113`) is applied at execution time, not at intent-build time. `intents/service.ts`'s completion flow never writes `amount` (its `ActivityInput` has no such field, see `docs/modules/api-intents.md`), so this row's `amount` stays `null` forever, even after the withdrawal confirms — a client-facing gap noted here rather than a bug: a future change could have the indexer backfill it from the vault's `withdraw` contract event, out of scope for this change.
- **`counterparty` on both pending rows is the vault contract address (`vault.address`, `TESTNET_VAULT.address` in production), not `null` and not the merchant's own address** — it's the value an activity feed renders for "who was this transaction with". `VaultRepo.recordPendingActivity`'s input carries `counterparty: string` explicitly because `createDrizzleVaultRepo(db)` — mirroring `createDrizzlePaymentsRepo`'s signature exactly — has no access to `vault.address`; only `createVaultService` (which receives the full `VaultServiceDeps`, including `vault`) can compute it, so it's threaded through the call the same way `PaymentsRepo.recordPendingActivity`'s `PendingPaymentActivity.counterparty` carries the payment destination (`payments/service.ts:23-30`) rather than the repo inventing it.
- **`SorobanSimulationError` is mapped to a FIXED sanitized token, never the error's own `.detail`.** `SorobanSimulationError.detail` (`../../lib/soroban-gateway.ts:34-39`) is explicitly documented as server-log-only — its own doc comment says HTTP layers "must map this error to a fixed short sanitized token ... never expose the raw diagnostic string to clients", mirroring `sponsor/submit.ts`'s `SubmissionFailedError.reason` convention. `service.ts`'s `runProviderCall` (`service.ts:158-167`) does exactly that: catches `SorobanSimulationError`, discards `.detail` entirely, and throws `AppError('simulation_failed', 'transaction simulation failed', 502, {detail: 'vault_simulation_failed'})` — a single hardcoded constant (`SIMULATION_FAILURE_DETAIL`, `service.ts:31`), not derived from or branching on the real diagnostic. `service.test.ts` asserts the raw diagnostic string never appears anywhere in the thrown error's `details`.
- **All three `VaultService` methods route through `runProviderCall`, not just `deposit`/`withdraw`.** `position()`'s `provider.getPosition` calls `soroban.simulateRead` internally (`defindex.ts:95-119`) — the exact same simulation failure mode as building a deposit/withdraw tx — so a live simulation failure while reading a position also needs the same sanitized 502 mapping, not an uncaught 500.
- **`asset = registry.get(vault.assetCode)` is resolved ONCE at `createVaultService` construction time, not per-request.** A misconfigured `vault.assetCode` not present in `registry` throws immediately when the service is built (same invariant `config/vaults.ts:25` already enforces at import time for the production `TESTNET_VAULT`/`TESTNET_REGISTRY` pair) — defense-in-depth on the injected deps, not a new runtime failure mode for real traffic.
- **`createSorobanSubmitter` fee-bumps at `SOROBAN_INVOKE_FEE` (`'1000000'`), not `wrapFeeBump`'s default `'10000'`.** Same floor as `defindex.ts`'s own `SOROBAN_INVOKE_FEE` constant and the adjustment noted in `api/scripts/spike-privy-stellar.ts:227-231`: a Soroban invoke tx's own inclusion fee is far above a classic payment's, and `TransactionBuilder.buildFeeBumpTransaction` rejects a `baseFee` below the inner tx's own per-operation fee rate. Verified in `submit.test.ts` by asserting the resulting `FeeBumpTransaction.fee` equals `1000000 * (innerOps + 1)` for a single-operation inner tx (`'2000000'`).
- **`createSorobanSubmitter` has no `tx_bad_seq`/`StaleSequenceError` classification, unlike `submitAndClassify` (Horizon).** `SorobanGateway.sendAndConfirm` throws `SorobanSubmissionError` with an already-short, already-sanitized `reason` (`'send_error'`/`'tx_failed'`/`'tx_not_found'`, `../../lib/soroban-gateway.ts:49-54`) — never Horizon's raw Axios error shape `resultCodes`/`sanitizedReason` decode — so `submitAndClassifySoroban` (`submit.ts:176-186`) passes `err.reason` straight through into `SubmissionFailedError`, with no stale-sequence special case. A genuinely stale merchant sequence number on a vault intent surfaces as a generic `submission_failed` 502 through `intents/service.ts`'s completion flow, not the more specific `intent_expired` 409 that Horizon-backed submitters (`createProvisionSubmitter`/`createPaymentSubmitter`) can produce.
