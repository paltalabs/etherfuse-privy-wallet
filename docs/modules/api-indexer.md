## Purpose

The `indexer` module is a standalone background worker (`api/src/worker.ts`, no HTTP surface). It runs two pollers per cycle: the Horizon poller and the ramp-status poller — **both live now** (the ramp poller is only skipped when `ETHERFUSE_*` credentials aren't configured, see Gotchas). The **Horizon poller** (`poller.ts`) reconciles the `activity` table against Stellar testnet ground truth: it polls Horizon's payments feed for every provisioned merchant and (a) confirms rows the API already wrote once it sees them land on-chain, (b) inserts rows for anything the API never knew about — external receives, or sends made outside this app entirely, and (c) confirms a still-`'pending'` ramp-owned `'off_ramp'` row it recognizes via cross-type match, closing the crash window where a payout's own completion flow never got to confirm it itself (see Gotchas). It is the only source of `'receive'` activity rows; `'provision'`/`'send'` rows are normally written first by `wallet`/`payments`/`intents` (`docs/modules/api-wallet.md`, `docs/modules/api-payments.md`, `docs/modules/api-intents.md`) and only get a fresh row from here if that write never happened (e.g. a crash between Horizon submission and the API's own DB write — see Gotchas).

The **ramp-status poller** (`ramp-poller.ts`) reconciles the settlement legs the Horizon poller structurally CANNOT see — the division of labor is: (a) a pix payin's fiat/pix leg through its FULL lifecycle (`'on_ramp'` rows — the Horizon poller never confirms these; confirming a payin has always been this poller's exclusive job, since only Etherfuse's own order status, not merely Horizon seeing a matching payment, proves the fiat leg settled), and (b) a payout's fiat-side EXCEPTION states only, for an `'off_ramp'` row that is STILL `'pending'` when this poller looks (refund/cancel before the on-chain leg ever confirmed) — most `'off_ramp'` rows are already `'confirmed'` by the time this poller runs, via the Horizon poller's own cross-type dedupe (`poller.ts:218-227`), and this poller's own DB query only ever selects still-`'pending'` rows, so it naturally skips every already-confirmed one. `createRampPoller` (`ramp-poller.ts:154`) re-fetches every pending `'on_ramp'`/`'off_ramp'` activity row tagged `externalRef: 'order:<orderId>'` (`ramp-poller.ts:53-79`'s `RampPollerRepo.listPendingOrderActivity`) against `RampProvider.getOrder` each cycle: `'completed'`/`'finalized'` confirms it — `'on_ramp'` additionally gets its `txHash` set from `OrderState.txHash` (nullable) and, only when the order supplied one, its `amount` OVERWRITTEN from `OrderState.amountTokens` (truncated to Stellar's 7-decimal precision, `formatStellarAmount`, `ramp-poller.ts:32-38`) — so a dishonest client echo (the row's amount is CLIENT-supplied at creation time, `ramp/service.ts`'s `createPayin`) cannot leave a permanently wrong ledger row once the order's own settled amount is known; `'off_ramp'` is confirmed with NO other column touched, since an off-ramp order's own `confirmedTxSignature` is Etherfuse-internal, never the merchant's payment hash (`docs/evidence/etherfuse-sandbox-findings.md` "## Anchor payment & completion"). `'failed'`/`'refunded'`/`'canceled'` marks the row `'failed'` (either type). `'created'`/`'funded'` are left untouched — sandbox orders have been observed to sit at `'funded'` for 2+ hours with no deadline after which pending can be assumed settled or failed, so this poller deliberately implements no timeout logic.

## Gotchas & invariants

- **Extending the shared `StellarGateway` interface with `listPayments` broke every existing fake `StellarGateway` object across the codebase's test suite — the same ripple `submitTransaction` caused when *it* was added (`docs/modules/api-wallet.md`'s Gotchas).** Every fake gateway literal in `app.test.ts`, `history/routes.test.ts`, `intents/routes.test.ts`, `intents/service.test.ts`, `payments/routes.test.ts`, `payments/service.test.ts`, `sponsor/submit.test.ts`, `wallet/routes.test.ts`, `wallet/service.test.ts` needed a `listPayments` stub added (all throw-if-called, since none of those modules' tests exercise it) as part of this same change. `POLL_INTERVAL_MS`'s addition to `EnvSchema` similarly required adding it to every hand-written `SpikeEnv` test fixture (`app.test.ts`, `history/routes.test.ts`, `intents/routes.test.ts`, `payments/routes.test.ts`, `wallet/routes.test.ts`).
- **The dedupe key is `(txHash, stellarAddress, type)` — NOT `externalRef`, unlike `intents/service.ts`'s `recordActivity` (`docs/modules/api-intents.md`'s Gotchas).** This module has no concept of an intent id; it only ever sees what Horizon reports. This works cleanly for `'provision'`: `wallet/service.ts` never writes a pending row itself, and `intents/service.ts`'s `complete()` only ever writes a `'provision'` activity row *with the real, final txHash already set* (either `'confirmed'` on success or `'failed'` with `txHash: null` — a failed one never matches a later real on-chain confirmation by txHash, so a *retried* provisioning intent's eventual success correctly produces a **second**, indexer-inserted row rather than incorrectly flipping the failed one).
- **The "API completion crashed mid-write" gap for `'send'` rows is now closed — `intents/service.ts` pre-computes and writes the final txHash onto the pending row BEFORE calling the gateway, not just after.** Previously, `payments/service.ts`'s `recordPendingActivity` wrote the pending `'send'` row with `txHash: null` at intent-*creation* time (`api/src/modules/payments/service.ts:62-76`), and the real txHash was only attached later, by `intents/service.ts`'s `recordActivity`, on completion — so a process crash *after* the submission successfully posted to Horizon but *before* `repo.markSubmitted`/`repo.recordActivity` ran (two separate, non-transactional `await`s) left the row permanently stuck at `txHash: null`, which `findActivity`'s dedupe lookup could never match against a real on-chain hash (`WHERE txHash = 'real...'` can't match `txHash IS NULL`), producing a duplicate `source: 'indexer'` row instead of reconciling the stuck one. The fix (`docs/modules/api-intents.md`'s Gotchas — `IntentsRepo.updateActivityTxHash`): `complete()` now resolves the intent's kind to its registered `IntentSubmitter`, computes the hash of the exact tx `buildSubmission` returns (the fee-bump for `'payment'`, the plain inner tx for `'provision'`), and writes it onto any matching pending row immediately after the atomic claim, before that submitter's `submit` is ever called. The same crash window now leaves the row `status: 'pending'` but with its real txHash already set, so `findActivity(realTxHash, address, 'send')` matches it and flips it to `'confirmed'` — no duplicate row. `'provision'` never had this gap (no pending row with a null txHash ever existed for it) and is unaffected. See `poller.test.ts`'s dedicated crash-window test for the exact scenario.
- **The cursor advances to the LAST RAW record's paging token, not the last *normalized* one.** `pollMerchant` (`poller.ts:179-184`) computes `newCursor` from `rawRecords[rawRecords.length - 1]` before filtering — if it advanced only past normalized/kept records, a batch that was entirely native-XLM/foreign-asset/non-payment-op (all `null`) would report `newCursor === undefined`-equivalent (no records to base it on) and the poller would re-fetch the exact same skipped page forever.
- **Cross-type dedupe (`RAMP_OWNER_TYPE`, `poller.ts:25-28,199-227`): a normalized `'receive'`/`'send'` record with no direct-type match is checked AGAIN against the sibling ramp-owned type before `insertActivity` runs.** A pix payin settling to the merchant's Stellar address shows up in Horizon's payments feed as an ordinary incoming payment — `normalizePayment` has no way to tell it apart from any other external receive, so without this check it would normalize to `'receive'` and get inserted as a SECOND row alongside the `'on_ramp'` row `ramp/service.ts`'s `createPayin` already wrote (`docs/modules/api-ramp.md`) — the same activity double-counted under two types. The Stellar payout leg is the mirror case: `ramp/service.ts`'s `createPayout` (pending) and the `'payout'`-kind `IntentSubmitter`'s completion write (`ramp/submitter.ts:28`, via `intents/service.ts`'s `complete()`) both write `'off_ramp'` rows for the SAME outgoing payment Horizon also reports as a plain `'send'`. Only `'receive'`/`'send'` are checked — `'provision'` has no ramp-owned sibling type and is unaffected (`RAMP_OWNER_TYPE` has no `'provision'` entry). The insert is always skipped on a hit, but what happens to the pre-existing sibling row now DIFFERS by type and status: an already-`'confirmed'`/`'failed'` sibling of either type is left completely untouched, same as before. A still-`'pending'` `'on_ramp'` sibling is ALSO left untouched here — confirming a payin stays `ramp-poller.ts`'s exclusive job, since only Etherfuse's own order status, not merely Horizon seeing a matching payment, proves the fiat leg actually settled. A still-`'pending'` **`'off_ramp'`** sibling, by contrast, IS confirmed right here (`tx.confirmActivity(rampOwned.id)`) — this closes a real crash window: the `'payout'`-kind `IntentSubmitter`'s completion flow (`intents/service.ts`'s `complete()`, via `ramp/submitter.ts`) pre-computes and writes the payout's real txHash onto the pending `'off_ramp'` row before submitting (the same mechanism as the `'send'` crash-window fix documented below), then is supposed to confirm that row itself on success — but if the process dies after the provider accepted the payout and it landed on Horizon, yet before `complete()`'s own success path ran, the row would otherwise be stuck `'pending'` forever. **As of Task 6, `ramp-poller.ts` DOES also query pending `'off_ramp'` rows now — but this specific crash window is still ONLY closed by the Horizon poller, not by `ramp-poller.ts`.** A row stuck pending purely because of this crash (Horizon already confirmed the payment on-chain, but `complete()`'s own success path never ran) has an Etherfuse order status of `'funded'` — the on-chain leg was detected, the fiat leg has not (yet) settled — and `'funded'` is NOT one of `ramp-poller.ts`'s terminal statuses (`TERMINAL_SUCCESS`/`TERMINAL_FAILURE`, `ramp-poller.ts:11-13`), so `ramp-poller.ts`'s own cycle leaves that same row untouched too; only the Horizon poller's cross-type dedupe (right here) can ever confirm it. See `poller.test.ts`'s cross-type tests: the `'on_ramp'` case (still-pending, left alone), the `'off_ramp'` already-confirmed case (plain skip), and the `'off_ramp'` still-pending case (confirmed here).
- **Known residual race — investigated and CONFIRMED live for Task 6's resolution 4: an `'on_ramp'` row this poller confirms with a `null` `txHash` (the sandbox's normal case for completed onramp orders) can NEVER be found by the Horizon poller's cross-type dedupe, permanently duplicating the payin's delivery payment as a second, indexer-inserted `'receive'` row.** `poller.ts`'s cross-type lookup matches on the EXACT tuple `(txHash, stellarAddress, 'on_ramp')` (`findActivity`, `poller.ts:220`) — it queries for the row using the REAL on-chain txHash Horizon just saw. If `ramp-poller.ts` confirmed that `'on_ramp'` row with `txHash: null` (because `OrderState.txHash` was null — `docs/evidence/etherfuse-sandbox-findings.md` "## Fiat received & settlement": "The completed ONRAMP order carries NO `confirmedTxSignature` in sandbox"), the row's `txHash` column stays `null` forever — there is no later cycle that fills it in. The lookup `findActivity(realTxHash, address, 'on_ramp')` therefore ALWAYS misses, `pollMerchant` falls through to `insertActivity`, and the SAME delivery payment ends up represented by two rows: the `'on_ramp'` row (confirmed, `txHash: null`) and a fresh indexer-inserted `'receive'` row (confirmed, the real hash) — permanently, not just until some later cycle catches up. **Deliberately NOT fixed by amount-based or other fuzzy matching** (per this task's own guidance — fragile matching invites worse bugs than the duplicate row it would avoid). The only correct fix is `ramp-poller.ts` writing a REAL `txHash` when one exists — it already does (`repo.confirmOnRamp(row.id, {txHash: state.txHash, ...})`, unconditionally forwarding whatever `OrderState.txHash` the provider supplied) — so this gap closes itself automatically the moment Etherfuse (sandbox or production) ever DOES report a `confirmedTxSignature` for a completed onramp order; nothing in this codebase needs to change. **Accepted as a known gap for the MVP**, same acceptance rationale this bullet always had: no automated regression test exists for it (it requires a live Horizon poll racing a live Etherfuse order, not something a fake gateway/provider can reproduce meaningfully), and it does not corrupt any single row's own status — it only double-counts the settlement in any UI/summary that sums `'receive'` + `'on_ramp'` rows together. Revisit if Etherfuse's production API is confirmed to always populate `confirmedTxSignature` on completed onramp orders (the gap would then never trigger) or once a webhook-driven settlement notification exists to close it structurally.
- **One Horizon page (default 50 records) per merchant per cycle, not a catch-up loop.** A merchant with a backlog of >50 unindexed payment ops takes multiple `POLL_INTERVAL_MS`-spaced cycles to fully catch up, rather than draining in one cycle. Acceptable for MVP-scale testnet volume; revisit (inner while-loop per merchant until a page returns fewer than `limit` records) if backlog depth becomes a real concern.
- **`HorizonPaymentRecord.type` is a plain `string`, not a literal union.** `PaymentCallBuilder`'s real return type (verified against installed `@stellar/stellar-sdk@14.6.1`, `lib/horizon/payment_call_builder.d.ts`) is a 6-member union (`PaymentOperationRecord | CreateAccountOperationRecord | AccountMergeOperationRecord | PathPaymentOperationRecord | PathPaymentStrictSendOperationRecord | InvokeHostFunctionOperationRecord`); `mapPaymentRecord` narrows on it internally (`stellar-gateway.ts:218,229`) but the *returned* `HorizonPaymentRecord`'s `type` field is deliberately widened to `string` so `normalizePayment` doesn't need to import stellar-sdk's operation-type union just to have an exhaustive-enough discriminant for its `if (record.type === 'create_account')` / `'payment'` checks — anything else already needs to fall through to the same `null` branch regardless of which of the other 4 real types it is.
- **`normalizePayment` takes `registry` as an explicit third parameter, deviating from this module's originally-sketched 2-arg signature (`normalizePayment(record, ownAddress)`).** The registry-filter rule (native/foreign-issuer/unknown-code assets must normalize to `null`) requires registry access; passing it explicitly (rather than a `createNormalizer(registry)` factory closing over it) keeps the function trivially pure/testable — every `normalize.test.ts` case constructs its own `AssetRegistry` inline.
- **`worker.ts` is a genuinely separate process from `server.ts`, with its own DB pool** — `pnpm dev` (root `package.json`) does not start it; run `pnpm worker` (root) / `pnpm --filter @paltalabs/api worker` alongside `pnpm dev` for local end-to-end testing. Not orchestrated together deliberately, mirroring a real prod split between an HTTP service and a background worker.
- **Ramp reconciliation now runs — this closes the "payin reconciliation unbuilt" gotcha this doc carried since the Etherfuse cutover.** Before Task 6, `worker.ts` built only the Horizon poller and `ramp-poller.ts`'s stub was never called, so nothing ever confirmed a pending `'on_ramp'` row at all. As of this change, `worker.ts`'s `buildRampPoller` (`worker.ts:25-41`) constructs a real `RampPoller` whenever all four `ETHERFUSE_*` credentials are present, and the ramp cycle runs every `POLL_INTERVAL_MS` alongside the Horizon cycle (see the try/catch bullet below). A deployment missing any of the four still runs chain-only (a one-line startup notice, not a crash) — deliberately NOT the fail-fast throw `server.ts` uses for the same four variables.
- **`ramp-poller.ts` never overwrites an `off_ramp` row's `txHash` or `amount`, under any status.** An off-ramp order's own `confirmedTxSignature` (surfaced as `OrderState.txHash`) is Etherfuse's OWN internal transaction, never the merchant's payment hash — live-verified: the merchant's self-built payment hash and the order's `confirmedTxSignature` were two DIFFERENT values in the same recorded run (`docs/evidence/etherfuse-sandbox-findings.md` "## Anchor payment & completion": ours was `9ec033df…`, the order's was `dda94302…`). `RampPollerRepo.confirmOffRamp` (`ramp-poller.ts:67-75` interface, `:111-112` impl) therefore takes no `txHash`/`amount` argument at all — there is no code path by which this poller could write provider data onto an `off_ramp` row's payment-identifying columns, not even by a caller mistake. `docs/modules/api-ramp.md`'s Gotchas independently documents the same invariant from the `ramp` module's side.
- **An `on_ramp` row's `amount` is OVERWRITTEN, not just confirmed, on `'completed'`/`'finalized'` — but only when the order actually supplied one.** `ramp/service.ts`'s `createPayin` records the row's `amount` from the CLIENT's own request (`centsToDecimal(request.amountCents)`, `service.ts:607` — the client echoes its own quote, since Etherfuse's order-create response carries no settlement amount at all, `OnrampOrderState`'s doc comment) — a trust boundary this poller closes once the order's own ground truth is known: `formatStellarAmount(state.amountTokens)` (`ramp-poller.ts:32-38`) replaces it. `amountInTokens` is present ONLY at `status: 'completed'` (`docs/evidence/etherfuse-sandbox-findings.md` "## Fiat received & settlement" — the `created` in-flight read carries none), so a `'finalized'`-status confirm with no `amountInTokens` in the read leaves the client-echoed amount as the best-available figure rather than clobbering it with nothing — see `ramp-poller.test.ts`'s dedicated null-amountTokens case.
- **`formatStellarAmount` FLOORS to 7 decimal digits — it never rounds — and this is verified correct against a live delivery, not assumed.** Etherfuse's `amountInTokens` carries up to 27 fractional digits (`"19.620062792064687229069147940"`, live-recorded), but the actual on-chain delivery for that SAME order was Horizon's `"19.6200627"` (`docs/evidence/etherfuse-sandbox-findings.md` "## Fiat received & settlement": `path_payment_strict_receive` of `19.6200627 USDC`) — truncating the raw string's first 7 fractional digits reproduces that exactly; rounding the 8th digit (`9`) up would not (`19.6200628`, never actually delivered). This also matches the shape every other Horizon-sourced `activity.amount` value already has in this codebase — always exactly 7 fractional digits, zero-padded (`normalize.ts`'s output, e.g. `"10.0000000"` — `poller.test.ts`/`normalize.test.ts` fixtures).
- **`created`/`funded` orders are left pending with NO deadline logic, by design.** Sandbox orders have been observed to sit at `funded` for 2+ hours (payin) and 10+ minutes with no `completedAt`/`trackingCode` (payout, `docs/evidence/etherfuse-sandbox-findings.md` "## Anchor payment & completion": "the sandbox's BRL fiat leg settles asynchronously (or not at all without operator action)"). `ramp-poller.ts` has no timeout/staleness concept — a row that never reaches a terminal Etherfuse status stays `'pending'` in this codebase forever, re-checked every cycle at no meaningful cost (one `getOrder` call). Revisit only if a genuine business need for a manual/timeout escape hatch emerges; nothing in the evidence suggests one is needed for the MVP.
- **Each poller cycle is wrapped in its own `try`/`catch` in `main`'s loop (`worker.ts:77-100`) — a Horizon-side failure and an Etherfuse-side failure are fully independent.** A transient Horizon outage logs `` `[indexer] cycle failed:` `` and skips straight to the ramp cycle (or the next sleep, if the ramp poller is disabled) in the SAME iteration, rather than skipping the whole cycle; symmetrically, a `RampProviderError` bubbling up from `ramp-poller.ts`'s own per-row catch (or any other error out of `rampPoller.pollOnce()`) logs `` `[indexer] ramp cycle failed:` `` without affecting the Horizon poller, which already ran earlier in the same iteration. Same resilience posture as the pre-existing single-poller catch this mirrors.
- **Signal handling was verified working correctly, but observing that through the `tsx` CLI is misleading.** `tsx <script>` (the `worker`/`dev` npm scripts both use it) spawns a *separate child* Node process to actually run the script — `ps` confirms two distinct PIDs (a `tsx/dist/cli.mjs` wrapper and a `node --require preflight.cjs ... src/worker.ts` child). Sending `SIGINT`/`SIGTERM` to the *wrapper's* PID (e.g. what a naive `kill $(pgrep -f worker.ts | head -1)` might hit, or what a shell's `wait` on a backgrounded `pnpm worker` job tracks) reports exit code 130/143 because the wrapper itself has no signal handler and dies on the raw signal immediately — independent of whether the real child (which DOES receive and handle the signal) finishes its own graceful `pool.end()` shutdown a moment later. Confirmed correct end-to-end by running `node --import tsx/esm src/worker.ts` directly (single process, no wrapper): `SIGINT` → `"received SIGINT, stopping after the current cycle"` → `"stopped cleanly"` → exit code 0. In real deployment (Docker/systemd, where a signal typically reaches the whole process group), this wrapper nuance is not expected to cause any actual problem — noted here only so a future debugging session doesn't mistake it for a bug in `worker.ts`'s own logic.
- **Live-verified against Stellar testnet** (spike merchant address from `docs/evidence/spike-keys.secret.json`, already public in committed evidence per that file's own history — not reproduced in this doc): a fresh local Postgres (`docker compose up -d db`, migrated) with that merchant seeded as `provisionedAt`-set produced **10 activity rows** on the first `pnpm worker` cycle — 1 `'provision'`, 7 `'receive'`, 2 `'send'`, all `status: 'confirmed'`, `source: 'indexer'`, `assetCode` matching the registry's tracked asset (or `null` for the provision row) — matching the registry-only filter (no XLM-only rows appeared). A second run against the same DB applied **0** new rows (cursor already past the batch), confirming idempotent re-polling.
