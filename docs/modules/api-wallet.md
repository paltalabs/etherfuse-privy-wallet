## Purpose

The `wallet` module is the merchant's Stellar wallet surface: sponsored account provisioning (idempotent) and live balance reads. It resolves the caller's Privy embedded Stellar wallet, upserts a `merchants` row, and — if the wallet doesn't exist on-chain yet — builds a sponsor-signed provisioning transaction (create account + trustline, sponsor pays all reserves/fees) and stores it as a pending `intents` row for the merchant to co-sign via Privy `rawSign`. Submission of the co-signed tx is the `intents` module's concern (`POST /intents/:id/complete`, `docs/modules/api-intents.md`), which is why `StellarGateway` (defined here, in `lib/`) also carries `submitTransaction` even though this module's own service never calls it. `GET /wallet` reports the merchant's address, provisioning status, and live Horizon balances filtered to the asset registry.

## Endpoints / Public surface

Both routes are registered inside `app.ts`'s authenticated scope (`api/src/app.ts:93-99`, alongside `intentRoutes` — see `docs/modules/api-intents.md`) — they require `Authorization: Bearer <Privy access token>` (see `docs/modules/api-auth.md`) and read `request.privyDid`.

| Method | Path | Response | Notes |
|---|---|---|---|
| `POST` | `/wallet/provision` | `200 ProvisionResponse` — either `{intentId, xdr, hashHex}` (pending, sponsor-signed) or `{provisioned: true, stellarAddress}` (already on-chain) | Idempotent: repeat calls while the on-chain account still doesn't exist return the SAME pending intent, not a new one. Throws `AppError('no_stellar_wallet', ..., 409)` (via `privyUser.resolveStellarWallet`) if the caller has no embedded Stellar wallet yet. |
| `GET` | `/wallet` | `200 WalletResponse` — `{stellarAddress, provisioned, balances: Array<{assetCode, assetIssuer, balance}>}` | Throws `AppError('merchant_not_found', ..., 404)` if `POST /wallet/provision` has never been called for this DID. `balances` is empty (not an error) only when the account isn't on-chain yet; any other Horizon/network failure while fetching balances propagates as a `500`, not an empty array (see Gotchas). |

## Gotchas & invariants

- **`StellarGateway` now has a `submitTransaction` method (added for the intents module).** `loadAccount` alone was enough for existence probing/balance reads/loading the sponsor account for tx building; the `intents` module's `POST /intents/:id/complete` needed actual submission, so `submitTransaction` was added directly to this shared interface rather than duplicated per-module — see `docs/modules/api-intents.md` for the consumer and `docs/modules/api-sponsor.md` for `createProvisionSubmitter`/`createPaymentSubmitter`, the only place it's called now (via each factory's shared `submitAndClassify` helper).
- **`submitTransaction` deliberately does NOT translate Horizon failures the way `loadAccount` translates a 404.** `loadAccount`'s 404 → `StellarAccountNotFoundError` translation works because stellar-sdk's call-builder path produces a typed `NotFoundError` to translate. `Horizon.Server#submitTransaction`, verified directly against the installed `@stellar/stellar-sdk@14.6.1` source, does NOT: its own `.catch` handler always re-rejects the raw Axios error unchanged (see `docs/modules/api-sponsor.md`'s Gotchas for the full finding and file trail). So `createHorizonGateway.submitTransaction` (`stellar-gateway.ts:182-185`) just lets `horizon.submitTransaction` reject as-is — there is no typed error to translate INTO. The consumer that needs to classify a submission failure (e.g. detect `tx_bad_seq`) duck-types that raw shape itself; see `sponsor/submit.ts`.
- **`StellarGateway` gained a third method, `listPayments`, plus a new exported type `HorizonPaymentRecord` (added for the indexer module).** This module (`wallet`) doesn't call either — the sole consumer is `modules/indexer/poller.ts` (`docs/modules/api-indexer.md`, which documents both in full: signature, the raw-Horizon-record-to-camelCase mapping, and every test). Noted here only because extending this shared interface broke every hand-written fake `StellarGateway` object across the codebase's test suite (this module's `service.test.ts`/`routes.test.ts` fakes included) — each needed a `listPayments` stub added (throw-if-called, since no test here exercises it), the same ripple `submitTransaction`'s own addition caused (bullet above).
- **The sponsor signs the provisioning tx at build time, not at submission time.** `service.ts:133` calls `tx.sign(sponsor)` immediately after `buildProvisioningTx` (the sponsor is the tx source per `provisioning.ts`), and the resulting XDR — already sponsor-signed — is what gets stored in `intents.xdr`. This means the `intents` module's completion flow only needs to attach the merchant's Privy `rawSign` signature (via `attachRawSignature`, `docs/modules/api-sponsor.md`) before submitting; it never needs the sponsor keypair again for this tx (`createPaymentSubmitter` still takes a `sponsor` param for `'payment'`-kind fee-bumps; `createProvisionSubmitter` doesn't need one — see `docs/modules/api-sponsor.md`/`docs/modules/api-intents.md`).
- **Idempotency is achieved with two separate checks, in order:** (1) "does the account already exist on-chain?" (`stellarGateway.loadAccount` success/failure — mirrors the same try/catch pattern `spike-privy-stellar.ts`'s `accountExists` helper uses) takes priority over (2) "is there already a pending intent?". This means a merchant who calls `/wallet/provision` after their intent was submitted+confirmed (but before this module's `provisionedAt` gets updated some other way) will correctly flip to the `{provisioned: true}` branch on their next call, even though a stale `pending` intent row might still exist in the DB (that row is simply never revisited once branch (1) starts succeeding).
- **`getWallet`'s `provisioned` boolean reads the DB row (`merchants.provisionedAt`), not a fresh Horizon check** — only `balances` is live. Since the `intents` module landed, `provisionedAt` DOES get updated by `POST /intents/:id/complete` on a successful `'provision'`-kind submission (`docs/modules/api-intents.md`) — but only through that path. If the on-chain account exists via some other route (e.g. a future indexer catching a submission this API didn't itself process), `provisioned` can still read `false` while `balances` is non-empty. Reconciling from raw chain state in that case remains a future indexer's concern.
- **`getWallet` requires a `merchants` row to already exist** (throws `AppError('merchant_not_found', ..., 404)` otherwise) — it does not fall back to resolving the Privy wallet on the fly. Call `POST /wallet/provision` at least once first.
- **Balance filtering matches by asset `code` AND `issuer` TOGETHER, never code alone — this is a security boundary, not a data-modeling nicety.** The merchant fully controls their own Stellar signing key and can add a trustline to *any* issuer at *any* time, entirely outside this backend (e.g. a phishing "airdrop" trustline using the real `USDC` code but a foreign issuer) — Horizon reports that balance exactly like a genuine one. Matching by code alone would display a spoofed asset as indistinguishable from the real `TESTNET_REGISTRY` entry it's impersonating. `getWallet` (`service.ts:156-173`) builds a `Set` of `` `${code}:${issuer}` `` pairs from `TESTNET_REGISTRY` via the `registryKey` helper and only reports Horizon balance lines whose exact `(assetCode, assetIssuer)` pair is a member — see the inline `SECURITY:` comment at the filter site. `WalletResponse.balances` carries `assetIssuer` on the wire specifically so this distinction isn't lost between backend and client (`packages/shared/src/api.ts:39-44`).
- **`getWallet`'s balance fetch only swallows `StellarAccountNotFoundError`, not every failure.** A blanket `catch { balances = [] }` would silently turn a real Horizon outage or network error into a false "empty wallet" — indistinguishable from a merchant who genuinely hasn't been funded yet. The `catch` block (`service.ts:174-181`) re-throws anything that isn't a `StellarAccountNotFoundError` (so it surfaces as the route's generic `500`, per `app.ts`'s error handler), and only collapses to `balances: []` for the one case that's actually expected: the account not existing on-chain yet. `provision()`'s `accountExists` helper (`service.ts:86-93`) deliberately keeps its original blanket catch — unchanged, out of scope for this fix — since a failed existence probe there simply falls through to "try to provision," which is the correct fallback regardless of failure reason.
- **Two separate `PrivyClient` instances exist in the running server** — `auth/verifier.ts`'s (token verification) and `wallet/privy-user.ts`'s (wallet resolution) — `server.ts:27,29` constructs each independently via their own `createXxx(appId, appSecret)` factory, mirroring `auth`'s established pattern rather than sharing one client instance across concerns. Minor duplicated overhead, deliberate decoupling.
- **`resolveStellarWallet` uses `client.wallets().list({user_id, chain_type: 'stellar', limit: 1})`**, not `client.users()._get(userID)` + scanning `linked_accounts` — both are valid per the installed `@privy-io/node@0.27.0` type declarations, but `wallets().list` returns `Wallet` objects (`{id, address, ...}`) directly, avoiding the discriminated-union narrowing `LinkedAccount`'s ~20 variants would require. See `privy-user.ts:19-35` for the full verification trail (exact `.d.ts` paths/lines).
- **`StellarAccount` (this module's account abstraction) is a plain interface, not `Horizon.AccountResponse`** — the latter is a class with a private field, so object literals (needed for cheap test fakes) can't satisfy it structurally. `StellarAccount`'s three methods match `stellar-sdk`'s `Account` class exactly (all public, no private members), so it's structurally assignable to `Account` with no cast — confirmed by `service.ts:126` passing a `StellarAccount` straight into `buildProvisioningTx`'s `sponsorAccount: Account` parameter.
- **`HORIZON_TESTNET_URL` is hardcoded in `server.ts` (`https://horizon-testnet.stellar.org`), not env-configurable** — the wallet MVP is testnet-only for now; no other value would currently make sense. Revisit if/when mainnet support is added.
- **`app.ts` constructs `WalletService` itself from `AppDeps`' raw pieces** (`db`, `stellarGateway`, `privyUserResolver`, `sponsorKeypair`, plus the module-internal `TESTNET_REGISTRY` and `Networks.TESTNET` constants) rather than `AppDeps` carrying a pre-built `walletService` — keeps `AppDeps` to generic injectable infra (matching `db`/`env`/`privyAuth`'s existing shape) and lets `routes.test.ts`'s end-to-end tests substitute fake `stellarGateway`/`privyUserResolver` without needing a working fake Postgres (see Testing).
